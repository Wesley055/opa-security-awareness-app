## 4. ADR-014 SECTION 11 - FOUR DECISIONS, ALL RECORDED BEFORE THEIR CODE
================================================================================

Section 11 was created at 407b616 and amended at 4ccba62 and ff2e556. It sits
at line ~593 in decision-log.md, inside ADR-014 (starts 218), before ADR-012
(starts ~617). ADR-014 section 10 remains at 519.

### 4.1 STORAGE ENGINE [D] - 407b616

The mobile Journey queue uses expo-sqlite. Selected because the queue requires
durable ordered rows, an explicit session identifier per fix, persisted
capture sequence across process death, and atomic removal only after
acknowledged delivery. AsyncStorage was rejected: enqueue and dequeue would
require serialising, parsing and replacing the entire queue of up to 600 fixes
on every operation. expo-secure-store remains reserved for small secrets.

The ADR also records three implementation constraints: preserve oldest-first
flushing, store the owning session with every fix, and persist the capture
sequence so restart cannot reuse an idempotency key.

[D] THE AGE-RETENTION CEILING IS EXPLICITLY NOT DECIDED BY THIS.
MAX_QUEUED_FIXES = 600 remains the independent depth bound. The time-based
limit remains an open PRODUCT decision, as Ultra 24 section 6 framed it.

### 4.2 PLATFORM BOUNDARY [D] - 4ccba62

The durable queue is supported on Android and iOS only. The Expo web target is
not an emergency-tracking client and gets no alternate implementation.
Initialization on web must FAIL CLOSED. The existing `web` script is a
development convenience and is explicitly not evidence that emergency tracking
must work in browsers.

[M] WHAT THE RESTRICTION BUYS, and this is recorded in the ADR so nobody
relaxes it casually: withExclusiveTransactionAsync is unavailable on web, and
the non-exclusive withTransactionAsync "can be interrupted by other async
queries" per expo's own docs. The queue's read-then-delete after acknowledged
delivery requires the exclusive form. Supporting web would require a separate
queue implementation with separately specified semantics.

### 4.3 REPLAY INTEGRITY [D] - ff2e556

After acknowledged delivery, the replay layer compares the number of
acknowledged idempotency keys with SQLite's `changes` count from the atomic
delete. A SHORTFALL IS AN INTEGRITY FAULT. The current replay cycle stops, all
remaining rows stay durable, a high-severity error records expected and actual
counts, and the client must not report complete success or continue flushing
later rows in that cycle.

[D] THE REASONING, WHICH MATTERS MORE THAN THE RULE: rows whose keys matched
have ALREADY been deleted atomically because the server acknowledged them. The
stop rule protects what remains rather than attempting an impossible rollback.
A nonzero shortfall is diagnostic of local key-identity drift, INCLUDING an
idempotency-key collision - other causes are possible, among them duplicated
acknowledgement keys, concurrent deletion, and corrupted local state - and
continuing past it compounds an unknown integrity failure. The remaining rows
stay durable and remain eligible for retry on a later scheduled flush; the rule
does not silently delete or skip them. Note that a PERSISTENT fault would stop
each subsequent cycle too, which is intended: a queue that cannot be reconciled
should surface repeatedly rather than drain quietly.

[D] AN EARLIER DRAFT PROPOSED LOG-AND-CONTINUE and was rejected. The argument
for continuing was that the fixes were already delivered so resending is
wasteful and the server dedupes anyway. The argument that won: a durable
emergency queue that silently continues past a DETECTED inconsistency is how a
system comes to report success while losing data. Stopping costs one flush
interval - 15 seconds. Recorded so the choice is visible rather than
inherited.

journey-tracker.ts lines 66-73 state that TrackedFix is EXACTLY the fields

### 5.3 WHAT INTEGRATION MUST STILL RESOLVE [R]

Three are decided in ADR-014 section 11; two are not decided anywhere.

  DECIDED:
  1. Persist captureSeq and read it back on start (meta table exists).
  2. Store session per fix (column exists).
  3. Compare deleteAcknowledged's return against keys sent; stop the cycle on
     shortfall (rule recorded 4.3).

  NOT DECIDED ANYWHERE:
  4. WHAT HAPPENS TO ROWS OWNED BY AN ENDED SESSION. The key embeds the

  5. WHERE OVERFLOW EVICTION HAPPENS NOW. MAX_QUEUED_FIXES = 600 is enforced

     no eviction. Ultra 24 section 6 warns the retention ceiling must not be
     set implicitly by an eviction policy written later. Writing eviction into
     the store WOULD BE setting it implicitly.

### 6.1 THE FULL QUEUE MECHANISM, MEASURED [M]

Ultra 24 section 6 describes journey-tracker.ts's queue. This session read

[M] flush() SENDS queue.slice(0, MAX_BATCH) - oldest first, 200 max - guarded
by a `flushing` boolean against re-entry. ADR-014 section 6's ordering
invariant is structurally preserved by the current implementation.

[M] THE PRE-START GUARD compares the fix timestamp against
trackingStartedAtMs, which is set BEFORE subscribing precisely so the cached
fix that watchPositionAsync replays on subscribe is measured against a start
time that already exists (line 300-302). The activation fix already holds that
position, so dropping it loses nothing.

[M] OVERFLOW SLICES FROM THE FRONT and logs. The evicted fix's key is gone
locally but the server may already hold it. Harmless today; relevant once
persisted.

[M] captureSeq DOES NOT RESET ON stopTracking. It is module-lifetime, not
tracking-lifetime, so within one process keys stay unique across start/stop
cycles. ONLY PROCESS DEATH RESETS IT.

### 6.2 THE UNCOUNTED CONSEQUENCE - KEY UNIQUENESS IS LOAD-BEARING TWICE [M]

flush() removes sent fixes with:
  queue = queue.filter((f) => sent[f.idempotencyKey] !== true);

DELETION IS BY KEY, NOT BY INDEX. That is what makes trap 74 safe under
concurrent enqueue - a fix arriving mid-flight is not removed by position.

BUT IT MEANS A KEY COLLISION DELETES BOTH FIXES WHEN ONE WAS SENT. captureSeq
resets to 0 on restart; a restored fix and a new one in the same session and
the same millisecond produce identical keys; the filter then drops both.

[M] THIS IS SILENT AND LOCAL. The server never sees it. No exception is
thrown. The only symptom is a fix that was captured and never delivered.
Ultra 24 section 6 names the captureSeq reset as a constraint but does not
name this consequence, and no document did until ff2e556.

[R] THIS IS WHY deleteAcknowledged RETURNS A NUMBER. It is the only mechanism
in the system that can notice.

### 6.3 THE trackerDebugState SEAM IS NARROWER THAN ITS NAME [M]

  export function trackerDebugState(): {
    running: boolean; sessionId: string | null; queued: number;
  }

That is all. NOT captureSeq. NOT the queued keys. NOT generation.

[M] GREPPED, NOT ASSUMED: one definition, three references, all in the spec
written this session. Nothing in the app consumes it. The shape is free to
change without a compatibility concern.

[R] WIDEN IT BEFORE WRITING INTEGRATION CODE. The claim 9c exists to make is
"the queue survives process death." captureSeq is now ADR-mandated to persist
and is not observable through any exported surface. A test cannot assert what
it cannot see. Note the two existing toEqual assertions in the spec pin the
exact object shape and will need updating in the same change - that is the
seam working, not a cost.

[M] A UNIT TEST CANNOT KILL A PROCESS. "Restart" has to be simulated with
jest.resetModules() and re-import, which does reset module scope and is a fair
proxy. IT IS A PROXY. Name it that way in the test title so no future reader
promotes "module state resets" into "survives process death."

### 8.2 TRAP #119 - PowerShell KILLS A PIPELINE ON GIT'S STDERR [M]

  git push 2>&1 | ForEach-Object { "push|$_" }

failed with a NativeCommandError on git's ordinary progress output ("To
https://..."), which git writes to STDERR. PowerShell turned it into a
terminating error record and ABORTED THE REST OF THE LINE, so the follow-up
`$LASTEXITCODE` and status checks never printed. THE PUSH ITSELF SUCCEEDED.
Reading the error as a failed push would have been wrong.

[R] RUN git push AS A PLAIN STATEMENT, NOT PIPED. This works and prints
everything:
  git push origin main; "head=" + (git rev-parse --short HEAD)
`2>$null` plus a separate state check also works. Never `2>&1 |`.
The same applies to `npm ls`, which writes unmet-peer warnings to stderr.

### 8.4 TRAP #121 - INVARIANT STRINGS THAT SPAN A LINE WRAP [M]

A docs installer asserted the literal:
  'Persisting `captureSequence` across process death'
against markdown wrapped at ~80 columns, where the text reads:
  ...deletion exact. Persisting
  `captureSequence` across process death is part of...
The newline sits inside the search string, so it never matched and the
installer threw - CORRECTLY, and BEFORE writing anything.

[R] CHOOSE INVARIANT ANCHORS THAT CANNOT SPAN A WRAP. And fix the ANCHOR, not
the prose: reflowing documentation to satisfy a checker inverts the
relationship between them.

[M] A SECOND, WEAKER ANCHOR IN THE SAME LIST was `'the expected'` with a
`-lt 1` comparison - a phrase that could match anywhere in an 82KB file, under
a test that passes on any count. Changed to `'and actual counts'` with `-ne 1`.
An invariant that cannot fail is not an invariant.

### 8.5 THE INSTALLER PATTERN IS NOW THE STANDARD FOR DOC AND FILE EDITS [R]

Proven repeatedly this session. The shape:

  1. REFUSE TO RUN unless git status --porcelain is empty.
  2. Read the file as BYTES; detect BOM; assert CRLF-only before editing.
  3. Assert the anchor matches EXACTLY ONCE; refuse otherwise.
  4. Assert the new content is NOT ALREADY PRESENT (idempotency guard).
  5. Apply, then assert every content invariant with `-ne 1`.
  6. Write bytes; READ BACK and compare; restore the original on mismatch.
  7. Run git diff --check; restore the original if it fails.
  8. For code installers, add a byte-equality check on files that MUST NOT
     change - `tracker-byte-unchanged` proved journey-tracker.ts was untouched.

Step 8 is what turns "I did not mean to touch that file" into an exit code.
