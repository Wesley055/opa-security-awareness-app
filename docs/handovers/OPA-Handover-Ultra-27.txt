### 2.1 ITEM 5 - HTTP 400 HEAD-OF-LINE POLICY - 97d0580 [D]

The defect Ultra 26 section 4 named is now decided. The full reasoning is in
ADR-014 section 11; the load-bearing measurements:

[M] HTTP 400 COVERS TWO CONDITIONS WITH OPPOSITE LIFETIMES.
`classifyJourneyFixes` tests `timestampMs > nowMs + MAX_FUTURE_SKEW_MS` - a
ceiling anchored to the SERVER'S CURRENT TIME, which MOVES. That rejection is
self-healing in principle. It also tests `timestampMs < floorMs` - a floor
anchored to session start, which NEVER moves. That rejection is permanent.

[M] MAX_FUTURE_SKEW_MS = 5 * 60 * 1000 DOES NOT BOUND THE RECOVERY TIME. It is
the server's tolerance. For a device clock running ahead by X, the row becomes
eligible at real_now + X - MAX_FUTURE_SKEW_MS. Recovery is governed by the
clock offset, which has no architectural upper bound. NO ESCALATION TIMER MAY
BE DERIVED FROM THIS CONSTANT.

[M] A SKEWED CLIENT CANNOT COMPUTE ITS OWN ELIGIBILITY. The condition is a
statement about the server's clock; recordedAt was minted by the device's.
From inside the device the condition always appears already satisfied. Any
future implementation needs an explicit server-clock reference.

[D] INTERIM RULE: on 400, retain every row, halt the cycle, surface a
persistent high-severity fault. No timer. No client-side inference about which
row is at fault. MESSAGE TEXT SHALL NOT BE PARSED TO CLASSIFY REPLAY OUTCOMES.

[D] ACCEPTED FALSE-POSITIVE CLASS, RECORDED DELIBERATELY: a future-skew
rejection blocks the queue for an unbounded period, and the fault raised for
it may resolve without operator action.

[M] MAX_FUTURE_SKEW_MS AND START_GRACE_MS ARE BOTH 5 MINUTES AND ARE
UNRELATED. One bounds implausible device-clock lead; the other tolerates a fix
captured just before the session row was written. They must not be collapsed
into a shared constant. START_GRACE_MS is STILL undecided in the ADR.

### 2.2 FAULT SEPARATION AND EVICTION RESTRICTION - 5088ca4 [D]

Two subsections, both surfaced by writing 2.1 rather than by planning.

[D] TWO INDEPENDENT FAULT SLOTS. `durabilityFault` keeps store-side operation
failures. A new `replayFault` carries server replay outcomes as a DISCRIMINATED
UNION - HTTP_400, HTTP_404, HTTP_409, DELETE_SHORTFALL - so no consumer parses
`message` to learn what happened. Neither slot may overwrite the other, and
ONE CATEGORY NEVER CLEARS THE OTHER.

[D] DELETE_SHORTFALL MOVED from durabilityFault to replayFault. A shortfall is
a disagreement discovered during REPLAY, not a store operation failure.

[D] CLEARING: replayFault clears when a replay cycle receives a 2xx, or on
explicit reset. durabilityFault clears when the failed durability operation
later succeeds, or on reinitialization.

[D] TWO DEPTH BOUNDS. MAX_QUEUED_FIXES = 600 is the ordinary steady-state
retention depth. MAX_FAULTED_QUEUED_FIXES = 6 * MAX_BATCH = 1200 is a
storage-safety ceiling used ONLY while replay is faulted. NEITHER IS STATED AS
A DURATION - TIME_INTERVAL_MS is a minimum interval, not a fixed cadence.

[D] NORMAL EVICTION IS SUPPRESSED while replayFault is non-null: no
trimToDepth, and enqueue does not enforce the 600 bound.

[D] THE EMERGENCY CEILING IS NEVER DEFERRED. Deferral protects an ordinary
replay batch from the steady-state trim; it must not disable the storage-
safety ceiling. While faulted, enqueue enforces 1200 inside its exclusive
transaction REGARDLESS of whether a flush is in flight.

[D] EMERGENCY EVICTION GETS ITS OWN DIAGNOSTIC, QueueEvictionDiagnostic. It is
a policy event - not a store failure and not a replay outcome - and it clears
neither fault slot.

### 2.3 ITEM 9 - TEST SEAMS ARE PERMANENT - 97f2b69 [D]

Ultra 26 section 6 listed `resetTrackerStateForTests()` and `flushForTests()`

### TRAP #127 - AN INVARIANT CONTIGUOUS IN THE SOURCE BUT WRAPPED IN THE
###            TARGET [M]

An installer invariant read `requires a separately approved evidence-retention
decision`. In the ADR text that phrase spans a line wrap between `separately`
and `approved`, so the contiguous string never appears and the count came back
0. The installer HAS a guard for this - `if (needle.includes('\n')) fail(...)`
- but it checks the NEEDLE, not whether the needle spans a wrap in the TARGET.
The needle is a clean single line, so the guard passed and the count failed.

  [R] AUDIT EVERY NEEDLE FOR WRAP-SAFETY BEFORE SHIPPING: each must appear
      within a single line of the target text.

### TRAP #128 - A NEEDLE AUDIT THAT ONLY READS THE SOURCE IS NOT AN AUDIT [M]

### TRAP #129 - A MULTI-LINE HERE-STRING ANCHOR PASTED INTO THE CONSOLE IS LF
###            AGAINST A CRLF FILE [M]

A patch script with `@' ... '@` anchors returned `anchor_a=0` and
`anchor_b=0`. The file is CRLF; the here-string arrived from the console as
LF, so no multi-line anchor could match. It failed closed - but the symptom
reads EXACTLY like "the text has changed", which is the misdiagnosis to avoid.

  [R] NORMALISE BOTH SIDES BEFORE MATCHING:
      $text = $raw.Replace("`r`n","`n")
      $anchor = @'...'@.Replace("`r`n","`n")
      and convert back on write. Then paste-versus-file cannot matter.
