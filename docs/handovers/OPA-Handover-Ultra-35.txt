2. 14A-1 AND 14A-2, AND WHY THEY LOOK LIKE THAT
================================================================================

  browser -> opasafety.com (Next route handler) -> OPA API

THE PATTERN WAS ALREADY DECIDED IN THIS CODEBASE AND WAS FOLLOWED, NOT
REINVENTED. lib/tracking.ts opens with `import 'server-only'` and argues
that if it reached a client component the API base URL would ship to the
browser and the capability token would be handled client-side, "which is
exactly what the same-origin bridge exists to prevent". An operator
credential reads a whole facility's live emergencies with resident names and
coordinates - strictly more powerful than a tracking link - so it gets the
same treatment.

  Tokens live in httpOnly cookies. Client JavaScript cannot read them.
  The login response body carries NO TOKENS - only whether it worked.
  The API hostname never reaches client code.
  localStorage was rejected: readable by any XSS on a page that will render
  resident names and live coordinates.

COOKIE SETTINGS, each deliberate:

  httpOnly  the point
  secure    production only, so local http development still works
  sameSite  strict - no cross-site flow needs them
  maxAge    access 900s matching JWT_ACCESS_EXPIRES_IN, so the browser drops
            it when the token dies rather than sending a corpse; refresh 30d

THE ACCESS COOKIE EXPIRING IS THE DESIGNED SIGNAL FOR 14A-3. Absent access
cookie plus present refresh cookie means rotate.

ROLE IS CHECKED IN THE BRIDGE ONLY TO KEEP RESIDENTS OUT OF THE CONSOLE, NOT
AS AUTHORIZATION. The API re-reads role from the database on every guarded
request and that is what decides. The claim in the login response could be
stale. A resident who got in would see an empty shell and 403s, which is a
confusing way to be told no.

LOGOUT IS LOCAL ONLY. There is no revocation endpoint on the API, so
clearing the cookies means the browser can no longer present the tokens -
which is the whole of what a browser-side logout can honestly promise. The
access token stays technically valid for up to 15 minutes. DO NOT DESCRIBE
THIS AS "SIGNING OUT EVERYWHERE".

/operator IS A STUB. It exists so the redirect lands somewhere real and the
login is testable. The session check is a server component redirect rather
than middleware, deliberately: middleware would need the Next 16
middleware -> proxy migration first, and a server redirect cannot be
bypassed by a route a matcher missed.

4. NEW DEBTS FROM THIS SESSION
================================================================================

4.1 OPERATOR SEATS REQUIRE A PERMANENT UNIQUE PHONE NUMBER FOR A FIELD
    NOTHING READS

User.phoneNumber is non-null and unique - inherited from consumer
registration, where the phone IS the point. An operator is a login. They do
not receive SOS alerts; only emergency contacts do.

The constraint bit twice tonight with only four users in the system:
+14694791451 was already on wesleycharles055@gmail.com from SOS testing, so
the seat took 09066538149 instead.

FIVE GUARDS AT ONE ESTATE MEANS FIVE PERMANENT, UNIQUE, UNCHANGEABLE
NUMBERS. There is no endpoint to update a phone number. This will be a real
obstacle at the first estate onboarding, and it is a design question, not a
bug.

4.2 THERE IS STILL NO PASSWORD CHANGE, RESET, OR PHONE UPDATE

AuthController has register, login, activate. Nothing else. Three related
holes in the same area:

  - no password reset (a locked-out operator cannot be recovered)
  - no password change (a weak password cannot be strengthened)
  - no phone number update (see 4.1)

THIS BECAME URGENT TONIGHT. The info@opasafety.com admin password was typed
in plaintext into PowerShell during this session and is in the console
scrollback and in PSReadline's persisted history file. That account holds
cross-tenant read access to every facility's emergencies.

  IMMEDIATE, BEFORE ANYTHING ELSE:
    Clear-History
    Remove-Item (Get-PSReadlineOption).HistorySavePath

  Then change that password. With no endpoint, that means a bcrypt hash
  written directly to the row - the same shape as the ADMIN promotions in
  Ultra 34 section 4.

An account self-service sprint is now overdue.

5. TRAPS ADDED
================================================================================

Numbering continues from Ultra 34.

#184  AN EMPTY QUEUE IS NOT NECESSARILY A BROKEN QUEUE. The facility
      incident list defaults to OPEN + ACKNOWLEDGED. A resolved incident is
      correctly absent. Check the status filter before diagnosing anything.

#185  THE FACILITY SNAPSHOT CANNOT BE BACKFILLED. Incident.facilityId is
      written at creation. Assigning a resident to a facility affects only
      FUTURE incidents. A demo needs an SOS triggered AFTER the assignment.

#186  A CREDENTIAL TYPED INTO Read-Host WITHOUT -AsSecureString IS ECHOED TO
      THE SCREEN AND PERSISTED TO PSReadline HISTORY ACROSS SESSIONS. It
      happened once tonight with a production ADMIN password. Use
      -AsSecureString for anything that is not disposable.

#187  A SINGLE-USE ACTIVATION TOKEN IS RETURNED EXACTLY ONCE AND STORED ONLY
      AS A HASH. Losing it means recreating the seat - which costs another
      permanent phone number, because the first one is now taken.

#188  UNIQUE CONSTRAINTS INHERITED FROM ONE ROLE BECOME OBSTACLES FOR
      ANOTHER. phoneNumber is unique because consumer registration needs it
      to be. Operators inherit the constraint and get no benefit from it.

#189  AN UNLICENSED M365 ACCOUNT IS AN IDENTITY WITH NO MAILBOX. It never
      gets one by waiting. The exception name says so:
      OwaUserHasNoMailboxAndNoLicenseAssignedException.

#190  A BROWSER-SIDE LOGOUT CANNOT REVOKE A TOKEN, ONLY FORGET IT. With no
      revocation endpoint, clearing cookies leaves the access token valid
      for up to 15 minutes and the refresh token until used. Say what it
      does, not what it sounds like.
