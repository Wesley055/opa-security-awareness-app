### 3.1 THE SERIOUS ONE - ALERTS GO TO THE WRONG CONTACTS [M]

MEASURED, not reported:
  +2349066538149  Blessing Love, NOT primary   received EVERY alert
  +2347037119196  Osa Osahun, PRIMARY          received NONE
  +14694791451    not in the contact list      appeared in dispatch logs

Setting Osa as primary did not change the outcome.

[M] **A user can update their emergency contacts and alerts still go to the
wrong people, silently, while the app displays the correct list.** In a safety
product that is the most serious defect found across the last two sessions.

### 3.2 WHAT IS NOT WRONG - RECORDED SO NOBODY RE-DIAGNOSES IT [M]

`incident-orchestrator.service.ts:103` calls
`emergencyContactsService.listForUser(userId)` and reads contacts FRESH from
the database at incident creation. `listForUser` returns ALL contacts ordered
`isPrimary: 'desc'`, not just the primary. Lines 118-145 then build one SMS,
one WhatsApp and one email row PER CONTACT.

The fan-out is correct. The read is fresh. Do not start there.

### 3.3 TWO CANDIDATE MECHANISMS, AND THE ONE QUERY THAT DECIDES [R]

1. **`isActive` FILTERING.** `incident-orchestrator.service.ts:104-106` does
   `contacts.filter((contact) => contact.isActive)` BEFORE building any
   notification row. A contact whose `isActive` is false - or was never set
   true on create - is excluded silently while still appearing in the app.

2. **A FROZEN OUTBOX PAYLOAD ON A REUSED INCIDENT.** Dispatch Phase 2c-1 stores
   a durable JSON payload at INCIDENT-CREATION time. Throughout testing the app
   repeatedly reported "existing emergency alert remains active" and REUSED the
   session. A payload written when the original incident was created would
   replay its original recipients forever.

**THE TEST: query `isActive` on Osa Osahun's row.**
  FALSE -> mechanism 1 is the whole story. A data or default-value bug.
  TRUE  -> the reuse path is the cause, and the fix is a DESIGN DECISION about
           whether a contact change should invalidate pending payloads. That is
           ADR-shaped work, not a bug fix. See Ultra 28 section 3.5.

[R] DO NOT FIX FROM THE SYMPTOM. The two mechanisms need different fixes and
one of them is not a fix at all.

[M] `+14694791451` appearing in dispatch logs while absent from the contact
list is the single strongest piece of evidence, and it points at mechanism 2 -
a contact that existed when the incident was created and has since been
removed. It is not conclusive.

### 3.4 THE OTHER FOUR [M]

**No password reset exists.** The sign-in screen offers Email, Password, Sign
In and "Create one". There is no "Forgot password?" path anywhere. Any user who
forgets is locked out permanently. This blocks a real pilot.

**Labels are TRUNCATED on the Emergency Contacts screen - ONE layout bug, not
three typos.** "Bac" (Back), "Remov" (Remove), "Set" (probably "Set primary"),
all clipped on the same view. Three clipped labels on one screen means
containers too narrow or a line clamp without ellipsis. The strings are
probably already correct. Fix the layout.

[R] THIS WAS NEARLY MISRECORDED AS A SPELLING MISTAKE. It was reported as
"back is spelt bac". Seeing the screen showed two more clipped labels beside
it, which changed the diagnosis from three string edits to one layout fix.

**FEATURE GAP, not a defect: the user cannot choose WHICH contacts are
alerted.** The orchestrator already fans out to every active contact, so the
capability exists at the API. What is missing is a selection surface.
[R] DESIGN THIS ALONGSIDE THE `isActive` QUESTION IN 3.3 - they are the same
field seen from two ends, and deciding them separately would produce two
incompatible answers.

**The website needs a visual and content pass**, carrying Ultra 28 section 9's
three claims. One has changed since: "SMS live" is NOW TRUE as of 6 August.
"Push live" remains FALSE - push.provider.ts is a stub. The hash-chain claim
remains UNVERIFIED.
