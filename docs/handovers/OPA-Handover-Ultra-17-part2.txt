### 9b.4 ADR-012 - DECIDED, INSTALLED, PUSHED

**The full text is at `docs/handovers/ADR-012-content.txt` and installed at
`decision-log.md:9`.** Summary of what was decided and why, so the reasoning
survives even if the file is not to hand:

**The position: RENAME the flag, PRESERVE the throw, permit production boot only
when mock-backed outputs are suppressed.**

`OPA_ALLOW_MOCK_PROVIDERS` -> **`OPA_BOOT_WITH_SUPPRESSED_MOCKS`**.

The old name reads as permission to expose fabricated data, which is why three
documents ban setting it in Azure. **The state production actually needs is one
mode: mock providers registered, outputs suppressed, boot permitted.** The
mechanism already produces that state; only its name was wrong.

Three states, exhaustive:
| Condition | Behaviour |
|---|---|
| No MOCK providers | Boot normally |
| MOCK + flag `=== 'true'` | Boot with a warning; mock-backed outputs remain null |
| MOCK + flag absent or any other value | Refuse to boot |

**The strict `=== 'true'` comparison is retained**, so the existing test pinning
`TRUE`, `True`, `1`, `yes`, `on`, `false`, `''` as failures applies unchanged.

**HARD rename, not transitional.** One known consumer, absent from Azure, and an
unrecognised variable fails closed.

**Message text decided.** Warning: *"Mock emergency-intelligence providers are
registered. Current response handling suppresses their outputs from user and
responder responses. Boot permitted because
OPA_BOOT_WITH_SUPPRESSED_MOCKS=true."* Error: *"Refusing to start because mock
emergency-intelligence providers are registered ({list}). The current response
builder is designed to suppress their outputs, but boot requires explicit
acknowledgement with OPA_BOOT_WITH_SUPPRESSED_MOCKS=true."*

**Note the wording "designed to suppress" rather than "are suppressed".** That
was a deliberate correction: at drafting time no test proved the invariant, and
an error message asserting an unproven guarantee is the same failure mode as a
provider reporting a delivery it did not attempt. **`194b32a` has since proved
it, but the phrasing stays honest about what a message can claim.**

**The suppression contract, as ADR-012 states it:**
- Emergency intelligence is **optional enrichment, not a prerequisite for
  incident creation**. Raw device coordinates remain available regardless.
- Each mock-backed section is omitted **independently, per provider**.
- The orchestrator **must continue to handle null enrichment**. **Its current
  tolerance is UNMEASURED** - asserted in ADR-015 section 4, flagged here as
  unverified. Gap 7.
- A suppressed mock provider must **never** surface fabricated data.
- **Before the flag may be enabled in production, tests must pin suppression
  behaviour for all six currently registered mock providers.** **DISCHARGED by
  `194b32a`.**

**Why that last clause changed during drafting, and it matters:** the first draft
deferred coverage to "the next provider added". That would have left the present
six untested while the retained throw guarded against drift it could not detect -
and the service's own comment names this layer as the thing that must hold once
the validator is relaxed. **ADR-012 is that relaxation.** Making coverage a
precondition rather than a future obligation is what turned a 15-minute rename
into a test-first sequence.

**Shares its rationale with ADR-015 section 6b:** a provider that reports what it
did not do corrupts a record whose value is that it can be verified.

### 9b.6 THE INSTALLER DISCIPLINE, IMPROVED

The ADR-012 installer went through four revisions under review, and three of the
changes are general lessons:

**1. PHASE 2 MUST BE ABLE TO FAIL.** The first version's read-back checks only
printed `FAIL` and exited 0. A damaged write would have ended in apparent
success. Fixed with a counter and `process.exit(1)`. **The strongest single check
is `written === plannedContent`.**

**2. PIN CONTENT WITH A SHA-256 OF EOL-NORMALISED TEXT, NOT A BYTE COUNT.** A
byte count passes for any file of the same size. Proven in testing: substituting
`suppressed` -> `suppresced` is same-length and defeats a length gate; the digest
caught it. Normalising CRLF to LF before hashing also makes the check survive a
harmless line-ending conversion in transit, which was also proven.

**3. USE ONE COUNTING METHOD THROUGHOUT.** Counting the anchor with `indexOf` in
phase 1 and a line-anchored regex in phase 2 measures two different properties.
**Exception, documented in the file: the idempotency guard uses the MORE
sensitive substring check**, so it aborts even if the ADR is merely mentioned.

**4. TEST THE INSTALLER AGAINST A REPLICA FIRST.** Five cases against a synthetic
860-line CRLF no-BOM decision log: clean run (exit 0), re-run (exit 1), LF source
(exit 0 - digest is EOL-agnostic), same-length tamper (exit 1), duplicated anchor
heading (exit 1, `count=2`). **All five behaved correctly and the real run needed
no retries.**

### 9b.8 ADR-014 - THE ENDED-SESSION FIX CONTRACT. FULL CONTENT, DECIDED, STILL OWED.

**Status when written: Accepted (design), Not Implemented.**

**THE PROBLEM.** `journey-ingestion.service.ts:107` throws
`ConflictException('Journey session has ended.')` for **any** fix addressed to an
`ENDED` session, before examining a single fix. A batch buffered across a
supersession is rejected **entirely**, including fixes captured while the session
was still open. **Item 10's airplane-mode test is exactly this scenario.**

**THE DECIDED CONTRACT.** A fix submitted against an `ENDED` session is:
- **Accepted** when `recordedAt < endedAt`
- **Permanently rejected against that session** when `recordedAt >= endedAt`
- **Retried** only for transient infrastructure failures

**Permanently invalid for this session** - a specific client error with a stable
body:
```json
{
  "code": "FIX_RECORDED_AFTER_SESSION_ENDED",
  "retryable": false,
  "resubmit": "reacquire",
  "sessionId": "...",
  "endedAt": "...",
  "recordedAt": "..."
}
```

**THE QUEUE RULE:**
```
2xx                                  -> delete
retryable=false, resubmit=reacquire  -> RE-TAG and resend, do NOT delete
retryable=false, no resubmit path    -> delete and record permanent rejection
network / 408 / 429 / 5xx            -> keep
anything ambiguous                   -> keep
```

**BATCHES ARE PARTITIONED, NOT REJECTED.** Per-item outcomes:
```json
{
  "accepted": ["idem-key-before-end"],
  "rejected": [{ "idempotencyKey": "idem-key-after-end",
                 "code": "FIX_RECORDED_AFTER_SESSION_ENDED",
                 "retryable": false, "resubmit": "reacquire" }]
}
```

**FOUR REFINEMENTS:**

**1 - `retryable: false` MUST NOT MEAN "DELETE" HERE, BECAUSE ISSUE 17.13 WOULD
TURN IT INTO SILENT PERMANENT LOCATION LOSS.** The tracker never stops when the
user leaves the SOS screen, and `if (running) return` means a second activation
no-ops **keeping the FIRST session's `sessionId`**. So after a supersession the
client keeps capturing fixes tagged with the **ended** session, every one with
`recordedAt >= endedAt`. Under a naive delete rule the app looks like it is
tracking and nothing is recorded - **precisely the emergency case, because
supersession happens when a NEW incident starts.** Hence `resubmit: "reacquire"`.

**2 - `endedAt` CAN BE NULL. SPECIFY IT.** A null `endedAt` on an `ENDED` session
means reject-and-reacquire, never accept. Do not leave it to a JS comparison
against `null`. **Also: `endedAt` is NOT currently selected** at `:97`.

**3 - SEQUENCING. THE PER-ITEM BODY SILENTLY BREAKS THE CURRENT CLIENT.** Today
the client deletes on 2xx; a half-rejected batch returning 2xx would read as full
success. **Server and client must land in the same commit, or the server change
ships after the client learns to parse the body.**

**4 - THE IN-ORDER FLUSH INVARIANT, WHICH 9c MUST PRESERVE.** `893d65a` orders by
`receivedAt DESC, sequence DESC`, correct **only because the tracker flushes in
capture order, oldest first.** If 9c retries an old batch AFTER newer ones
succeeded, the newest `receivedAt` would carry the OLDEST `recordedAt` and the
tracking page would show a stale position as current. **Either 9c preserves
in-order flushing as an explicit invariant, or the latest-fix query moves to
`recordedAt`.**

**OPEN SCOPE QUESTION.** The skew checks at `:114-127` throw from inside
`.map()`, so one bad `recordedAt` 400s the whole batch - the same defect ADR-014
fixes for ENDED, and the same shape as 17.6's negative-speed gap.
**Recommendation: one policy, applied to all.**

### 9b.9 ADR-013 - EVIDENCE ARCHITECTURE. CONTENT DECIDED, STILL OWED.

**1. Priority ordering, and evidence must never delay location.**
```
location -> SOS/status messages -> telemetry -> audio -> photos -> video
```
A 200-fix batch is a few KB; thirty seconds of video is several MB. **On a weak
connection during an emergency, video would starve location updates - degrading a
proven capability to add an unproven one.** They use different endpoints, so the
priority queue is client-side scheduling across two transports.

**2. AUDIO ABOVE PHOTOS.** A phone in a purse produces twenty unusable photos;
a microphone in the same purse still captures speech.

**3. THE BINDING CONSTRAINT ON AUDIO IS BYSTANDER CONSENT, NOT USER CONSENT.**
The user cannot consent on behalf of the shopkeeper or passer-by whose voice ends
up in the file. **A question for counsel about a specific jurisdiction, not a
design toggle** - and the one item that genuinely blocks on NDPA. **An audio
recording is only evidence if it is admissible**; a file captured without a
defensible basis invites a challenge to the whole record, including the location
half that currently IS clean.

**4. THREE INTEGRITY MECHANISMS, ONE TIMELINE.** Location fixes have a **hash
chain** (proves nothing was REMOVED); evidence has **per-object sha256** (proves
a file was not altered); **the timeline is chained too**. A chain is strictly
stronger. **Folding location into per-object evidence would WEAKEN it.**

**5. AI SUMMARIES ARE NOT EVIDENCE OBJECTS.** The first competent challenge
attacks the summary and discredits everything adjacent. Derived material belongs
in a separate, clearly-labelled layer that REFERENCES evidence.

**6. DEVELOPMENT AND DEPLOYMENT ARE SEPARABLE.** The pipeline can be built while
capture release waits on regulatory work - and most of it already exists.

**7. RESPONSE COORDINATION - DEFERRED, NOT REJECTED.** Independence is the only
structurally uncopyable advantage: **a responder cannot produce neutral evidence
about their own response.** **The hash chain does NOT rescue this** - tamper-
evidence is not independence. **The boundary while deferred: VIEWER, NEVER
CONSOLE.** Incident list, live position, report retrieval, acknowledgement
display - yes. Responder assignment, status tracking, escalation - no. **Stated
explicitly because a viewer drifts into a console one reasonable request at a
time.** Recording that a responder acknowledged at 14:02:40 is *observing someone
else's action* - which is why acknowledgement is so valuable.

**8. PARTNER APIs COME AFTER PRODUCT-MARKET FIT** (`TODO.md:1335-1339`):
*pilot -> users -> reliability -> partners ask -> API.* The first realistic
integrators are **things that HAVE A TRIGGER BUT NO BACKEND**.
