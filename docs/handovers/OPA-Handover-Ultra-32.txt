## 2. THE SMS TRUTHFULNESS FIX - 4c664db [BUILT]
================================================================================

### 2.1 The defect

[M] Africa's Talking reports per-recipient failure INSIDE a successful HTTP
response. `sms.send()` does NOT throw when a message is rejected - the outcome
sits in `SMSMessageData.Recipients[n].status` as a string.

The provider returned `success: true` whenever the call did not throw, reading
`Recipients[0]` only for its `messageId`. The 6 August production sending log
shows the consequence:

    OPAALERT  +2349066538149  NGN 5.4000  Success
    OPAALERT  +2347037119196  NGN 5.4000  Sent
    OPAALERT  +2347037119196  NGN 5.4000  Failed

OPA recorded ALL of them as SENT.

[D] Same class as the three stubs, in the fourth provider - and worse, because
a FALSE record is worse than a missing one. ADR-015 section 6b.

### 2.2 The rule

[D] **"Success" IS THE ONLY ACCEPTED SEND-TIME STATUS.**

Failed, InsufficientBalance, UserInBlacklist, an unrecognised string, a
missing status field, an empty Recipients array, a malformed response - ALL
return `success: false`, with the provider's own status preserved in `error`.

**AN UNKNOWN PROVIDER STATE MUST NEVER BECOME A SUCCESSFUL DELIVERY RECORD.**
Failing closed is the only safe default for a safety product.

[M] Nothing changed outside the provider. `notification.service.ts:151-163`
already routes `success: false` to `status: FAILED` with `lastError` set from
the response, so the reason lands in the database per notification rather than
only in a log line.

### 2.3 The semantics, named in the code

[D] **send-time provider success != final delivery confirmation**

"Success" means Africa's Talking ACCEPTED the message. The carrier has
confirmed nothing; that arrives later through a delivery-report callback OPA
has no endpoint for.

[R] The comment exists because in six months somebody will read a SENT row as
proof a handset received the message, and from there it reaches a report and
then a customer.

### 2.4 A one-time mode log

[BUILT] On the first send of each process:

    [SmsProvider] mode=SANDBOX (simulator - NOTHING IS DELIVERED) username=sandbox
    [SmsProvider] mode=PRODUCTION username=OPASafety

[R] Ten lines that would have saved hours. Two separate defects were diagnosed
before anyone checked the username.

[R] IT DOUBLES AS A DEPLOYMENT MARKER. Once Azure restarts on this build, the
first SMS attempt prints that line. If it is absent, Azure is still running
the OLD build - a better signal than `/health`, which returns 200 either way.

### 2.5 Scope was enforced, not promised

[D] The three stubs are DELIBERATELY NOT in this commit. Same class of defect,
but combining four providers into one change immediately before a beta is
unnecessary blast radius. The installer read whatsapp/push/voice/email
.provider.ts and notification.service.ts before editing and asserted them
BYTE-IDENTICAL afterwards.

### 2.6 Tests

[M] Twelve, in a new `sms.provider.spec.ts`. Success accepted with its
messageId. Failed rejected - the exact case from production. Five other
statuses including an invented one. Missing status. Empty Recipients.
Malformed response. A thrown error. Absent credentials with no send attempted.

[R] The provider is loaded DYNAMICALLY inside `beforeEach`, after the mock
exists. A static import would bind the class BEFORE the mock is installed, and
`jest.resetModules()` does not rebind an already-imported reference - so the
lazy `require('africastalking')` inside `send()` would resolve against
whatever was in the registry when the class first loaded. The tests would then
pass or fail depending on module-cache state, which is worse than failing
outright.

## 9. TRAPS

### TRAP #151 - THE ENVIRONMENT IS THE FIRST HYPOTHESIS, NOT THE LAST [M]

Three times in three days a defect was diagnosed in the code when the answer
was which API, which database, or which provider mode was in use. Each cost an
hour or more, and in one case a whole correction document was written and had
to be reverted.

  [R] WHEN AN OBSERVED BEHAVIOUR CONTRADICTS THE CODE, CHECK THE ENVIRONMENT
      BEFORE RE-READING THE CODE. And instrument it: one log line naming the
      provider mode would have made all three visible in seconds.

### TRAP #152 - A LOG THAT ANSWERS THE WRONG DAY [M]

The Africa's Talking sending log showed one number failing and another
succeeding, which looked like a complete explanation. EVERY ENTRY WAS FROM
6 AUGUST. It could not explain failures observed on the 8th. A correction was
drafted around it at 4am and reverted the next morning.

  [R] CHECK THE DATE RANGE OF ANY EXTERNAL LOG BEFORE REASONING FROM IT. An
      empty result for the period you care about looks identical to a
      populated one when you do not filter.

### TRAP #153 - A GUARD THAT COMPARES THE WRONG UNITS [M]

An installer nearly shipped asserting that a file's byte growth equalled its
character delta. The file is written as CRLF while the delta counts
LF-normalised characters, so byte growth exceeds it by the number of newlines
added. The assertion would have failed on CORRECT output.

  [R] Same family as #146. A guard is only as good as the property it
      measures, and "bytes" and "characters" are not the same property.
      Verify a new guard against a synthetic case before trusting it.

### TRAP #154 - A REPORTED GATE THAT IS NOT AN ENFORCED GATE [M]

An installer ran four gates, printed all four results, and checked three in
its GREEN condition. The targeted test could have failed while the script
declared success.

  [R] Same shape as #148. If you declare N gates, enforce N gates. A result
      that is printed and not checked is decoration.
