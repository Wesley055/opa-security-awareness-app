# Durable approval for the legacy production API

Status: implemented candidate; signing, Linux/App Service rehearsal and production acceptance pending.

The version-1 shared policy envelope applies expiration to every API read. API configuration validation, initial database identity verification and SSO initialization reread this envelope. Container recycle, scale-out and recovery start the same code. Notification initialization also consumes API preflight. An expired envelope can therefore prevent an unchanged emergency API from starting. Migration admission uses the same verifier with a distinct purpose.

Version-1 verification remains unchanged. A separately signed version-2 `runtime-api` document authorizes one exact deployment ZIP's file inventory and one exact API configuration, resource identity and build. It has an issuance timestamp and deliberately has no expiration field. Only production API `readPolicy` can consume it. Its nested API configuration passes the existing resource, role, endpoint, setting and secret-digest checks. It is not an extension of a version-1 approval and cannot be inferred from an expired approval. Issuance requires separate explicit signing approval for the new corrected artifact.

The trusted registry is unchanged. The authorization binds the signer's SPKI fingerprint. A distinct signed `runtime-custody` record has a sequence, resource ID, explicit active authorization payload digests and revocations by authorization ID and authority fingerprint. Missing, malformed, future-issued, unsigned, revoked or mismatched custody denies admission. A signed minimum custody sequence prevents acceptance below the authorization's floor. Deployment, migration and signing workflows continue requiring their own unexpired approvals; runtime custody cannot authorize those purposes.

Artifact manifest and custody live outside deployed code at fixed `/home/opa-runtime-custody` paths. On each admission, every deployed regular file and relative in-tree symbolic link must match the signed inventory, including verifier, compiled API, dependencies, Prisma client and migration files. Extra and removed files fail. The deployment must be immutable: run-from-package or equivalent verified read-only mounting, no writable deployment contents or package installation at runtime. Configuration cannot redirect the trusted registry, manifest, custody location or artifact root.

Before API admission and every 60 seconds, fetch current signed custody from the existing signed Key Vault origin, latest secret version `opa-api-runtime-custody` over HTTPS using App Service managed identity. The identity must have read-only permission, while the custodian alone writes current state. Redirects, HTTP failure, unavailable identity and invalid signatures fail closed. No local-only fallback is permitted. The downloaded record is authenticated before atomically updating the cache; lower sequences and different bytes at the same sequence are rejected. TLS plus the authoritative latest Key Vault secret version prevents a restored local cache from authorizing startup. Custody writer rollback remains a privileged custody action and must retain the audit ledger.

Existing processes reverify signed custody and configuration every 60 seconds, terminating on revocation or custody failure. This check avoids hashing all dependency files on the request-serving event loop. Full artifact validation happens at admission. This relies on immutable deployed code; changing executable files in a live writable deployment is not supported. Workers within the Nest process terminate with it; any independent process must run the same admission and custody supervision before accepting work. Automatic managed-identity token refresh does not renew deployment approval and needs no human signature. Maximum revocation enforcement latency is 60 seconds plus bounded identity/Key Vault request timeouts and scheduling. A custody-service outage intentionally fails closed; monitor it as an availability dependency.

Custody is a privileged operational boundary. The sequence floor is not a global anti-replay oracle. Protect the authoritative Key Vault secret from application writes, retain version history and prevent unauthorized restoration of earlier signed state. An administrator able to overwrite both verifier and trusted registry remains outside this mechanism. Keep an append-only external operations ledger and independently verify its latest sequence before any privileged custody restoration. If existing App Service/Key Vault access cannot enforce immutable code and read-only runtime access to authoritative custody, rollout is blocked. A writable local cache is never the authoritative custody source.

The candidate uses the preserved recovery source b02a851 and canonical Linux recovery ZIP, with exactly 35 unchanged migrations. It does not use API42 or relax database readiness to accept pending migrations. Future builds require their own artifact-bound runtime authorization and coordinated schema compatibility review.
