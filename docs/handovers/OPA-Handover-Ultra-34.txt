2. WHAT THE COMMAND CENTER BACKEND NOW DOES
================================================================================

The whole chain exists in code and is reachable in production:

  bootstrap an ADMIN (manual, one-off)
    -> create a Facility
      -> provision a FACILITY_OPERATOR seat with a single-use activation token
        -> operator activates and chooses a password
      -> find a resident by exact email or phone
      -> assign the resident to the facility
    -> resident triggers SOS
      -> the incident snapshots User.facilityId at creation
        -> only that facility's ACTIVE operators can read it

2.1 FACILITY ROUTING (c7a2d43)

Incident.facilityId existed and nothing set it. Now IncidentsService.create
reads the subject's membership and freezes it onto the incident, inside the
same transaction as the insert.

  facilityId is SERVER-DERIVED. It is not on CreateIncidentDto and cannot
  be. A test asserts that a request body carrying facilityId is ignored -
  the difference between "we route incidents to facilities" and "a client
  can post an emergency into any estate's queue".

  The RE-TRIGGER path deliberately does not set it. A resident who joins an
  estate between activations must not retroactively pull an older incident
  into that estate's queue.

  NO ADVISORY LOCK, deliberately, and this reverses an earlier decision in
  the same session. Nothing in the codebase writes User.facilityId at that
  point, so a lock served no counterparty. 13C-3 later added the writers;
  they take the 1-arg user lock, but create() still does not. IF TWO
  SIMULTANEOUS WRITERS EVER MATTER, BOTH SIDES NEED THE LOCK - one alone
  does nothing.

2.2 OPERATOR AUTHORIZATION (bd30be5)

UserRole.HOSPITAL_STAFF replaced by FACILITY_OPERATOR. Measured first: zero
rows held the old value in production or locally, which is what made a
destructive enum rebuild free. It is only free once.

  FacilityType already carried HOSPITAL, POLICE_STATION, FIRE_STATION,
  SECURITY_PROVIDER, NGO, GOVERNMENT_AGENCY and OTHER. A role named after
  one of seven cases would have been inherited by every guard written after.

2.3 ACCOUNT LIFECYCLE (368c176)

  accountStatus  ACTIVE | PENDING_ACTIVATION   the activation lifecycle
  isActive       boolean                       administrative suspension

Two fields, two meanings, one owner each. DISABLED is deliberately absent
from the enum: isActive already owns suspension, and a third value would
duplicate it.

passwordHash became NULLABLE. A provisioned seat has never chosen a
password, and a placeholder credential would be a hashable value nothing can
match but every reader must reason about.

2.4 PROVISIONING (7133931, a8492d9, 187b6c6)

ADMIN-only. Creates facilities and operator seats, assigns and removes
residents, looks residents up, lists facility membership.

  REMOVAL IS FACILITY-SCOPED: DELETE /admin/facilities/:facilityId/residents/
  :userId. The facility in the route is the admin's EXPECTED membership, and
  a mismatch is 409. Without it a stale admin screen detaches a resident from
  whichever estate they were moved to.

  ASSIGNMENT STAYS LAST-WRITE-WINS, deliberately, and the controller says so.
  Assigning STATES where somebody belongs; removing REVERSES a specific
  membership. The asymmetry is intentional.

  findResident TAKES EXACTLY ONE IDENTIFIER, enforced in the service because
  class-validator has no XOR and a custom ValidatorConstraint would be a new
  abstraction for one invariant. A non-USER match returns null, not an error:
  the question is whether a RESIDENT exists, and disclosing that an operator
  account exists answers something the caller did not ask.

2.5 ACTIVATION (b0b3445)

POST /auth/activate, public and unauthenticated because the operator has no
credentials yet - that is what they are there to create.

  THE TOKEN IS IN THE BODY, NOT THE URL. 13C-3 returns the path
  /operator/activate/<token> for the future web page; that page posts it. A
  capability in a URL lands in access logs, proxy logs and browser history.

  ONE FAILURE MESSAGE FOR EVERYTHING. Deliberately unlike
  IncidentAccessTokenService, which distinguishes EXPIRED from REVOKED
  because a family watching a tracking link needs to know which. Here the
  caller holds a guess; saying "expired" confirms a token once existed.

  THE RE-READ UNDER THE LOCK IS WHAT MAKES IT SINGLE-USE. Two simultaneous
  posts both pass the pre-lock lookup, then serialise. The first nulls the
  hash; the second sees null and fails.

2.6 THE OPERATOR QUEUE (bda2d6c)

Before: every incident ever routed to a facility, unpaginated, each with its
full hash chain, every notification and every evidence record.

Now: compact projection, default OPEN + ACKNOWLEDGED, optional exact status,
cursor pagination at 25 with a 100 ceiling, ordered createdAt DESC id DESC
against a new composite index.

  THE CURSOR IS AN OPAQUE COMPOUND SEEK, not Prisma's cursor: { id }. Prisma
  resolves a cursor row by unique id regardless of the facility and status
  filter, so an id from another facility's queue would still find a
  position. The predicate mirrors the ordering exactly.

  NOTHING OPA CANNOT POPULATE HONESTLY. No acknowledgedAt, no ETA, no
  battery or device state. public-incident-snapshot.dto.ts set that rule:
  such a field is OMITTED, because a null implies the capability exists and
  is merely empty. THE WEBSITE PROMISES ETA AND PATIENT CONTEXT. It has
  neither.

  NOTHING WRITES IncidentStatus.ACKNOWLEDGED. Measured: every status write
  is OPEN plus the terminal states. The default names both live states
  anyway, and the service says why so nobody hunts for a bug.

3. THE SECURITY DEFECT NOBODY WAS LOOKING FOR
================================================================================

RefreshTokenService.rotate() verified the token SIGNATURE and nothing else.
No database read at all. It copied sub, email and role out of the payload
into a new access token AND A NEW 30-DAY REFRESH TOKEN.

SUSPENSION DID NOT SUSPEND. isActive=false stopped login() and nothing else:
the holder kept minting access tokens for 30 days, and because every
rotation issued a fresh refresh token, the window rolled forward
indefinitely. There was no revocation path at all.

The same held for every other lifecycle change. A demoted admin kept
role: 'ADMIN' in every rotated token. A PENDING_ACTIVATION seat, or a
deleted user, passed through untouched.

Fixed in 511834d: rotate() reads the row, rejects unless it exists, isActive
and accountStatus ACTIVE, and mints from the database rather than the
payload. THE STALE ROLE CLAIM IS IGNORED, NOT REJECTED - a legitimate
promotion must not force a logout.

HOW IT SURVIVED: all three guards re-read from PostgreSQL, and each says in
its own doc comment that authorization must reflect current truth. The
principle was written down three times and absent from the one place that
MINTS the credentials. Nobody read the token service because it looked like
plumbing.

fd78eee then closed the smaller version of the same gap: FacilityOperator
Guard and IncidentAccessGuard did not check User.isActive, so a suspended
operator kept their facility's queue for the 15-minute access token
lifetime. AdminGuard already checked it. Three guards, one principle, two
answers.

  THE OWNERSHIP BRANCH IS UNTOUCHED AND TESTED. IncidentAccessGuard returns
  true for the incident's owner BEFORE any user lookup. A suspended person
  still sees their own emergency record - suspension is an operator-
  privilege action, not a reason to hide somebody's safety history from
  them. The obvious version of that edit would have taken it away silently.

5. THE MIGRATION GUARD, AND WHAT IT DOES NOT DO
================================================================================

74c1b3d adds a migration-guard job to main_opa-api-production.yml.

  push, no migration files changed   -> build, test, deploy as before
  push, migration files changed      -> build and test run; DEPLOY BLOCKS
  workflow_dispatch                  -> guard skipped entirely

THE MANUAL DISPATCH IS THE ACKNOWLEDGEMENT, and it happens AFTER the
migration. A commit-message token or a checked-in "last applied" file would
both be claims made BEFORE the operation, and both can be wrong. Re-running
the failed push in the UI stays a push event and stays blocked, which is
correct.

Build still runs on a migration-changing push. A schema commit should prove
it compiles; the human is needed at the production boundary, not the
compiler.

THE RANGE IS THE WHOLE PUSH - github.event.before to github.sha, with
fetch-depth 0. The default shallow checkout has no HEAD^ at all, and today's
three migrations arrived in three separate commits, so a last-commit check
would have missed two.

AN UNUSABLE RANGE FAILS CLOSED. A force push gives an all-zeros before.

WHAT IT HAS NOT DONE: the blocking path has never run for real. Only the
quiet path is proven, by run #167 and by local git diff against three
ranges - one migration detected, one code-only push correctly silent, one
multi-commit range catching all three. The first migration-bearing push is
its first live test, and the failure mode there is a blocked deploy, not a
broken production.

THE PROCEDURE IT TELLS YOU TO FOLLOW EXISTS NOWHERE. The guard says "apply
from an approved environment inside the production VNet" and deliberately
does not name commands, because the working invocation depends on accidental
runtime state (below) and a stale command in a permanent file will be
followed. THERE IS NO RUNBOOK. Write one.

HOW TO APPLY A PRODUCTION MIGRATION, as of 13 August:

  Portal -> App Services -> opa-api-production
         -> Development Tools -> SSH

  cd /home/site/wwwroot
  node node_modules/prisma/build/index.js migrate status --schema prisma/schema.prisma
  node node_modules/prisma/build/index.js migrate deploy --schema prisma/schema.prisma

  NOT ./node_modules/.bin/prisma - that shim resolves its wasm against

  AND THIS IS ACCIDENTAL. prisma is a devDependency and the workflow runs

  docker-compose.yml, _del_node_modules, node_modules.tar.gz - not the clean

MIGRATE BEFORE DEPLOYING, NOT AFTER. New code reads columns the old schema
does not have, and /health stays green while login returns 500.

7.2 THERE IS NO RATE LIMITING

Measured: no ThrottlerGuard, no APP_GUARD, no @Throttle, no SkipThrottle

SPRINT_ROADMAP.md:303 says "basic rate limiting already real, ThrottlerModule

7.3 THE JWT CARRIES A ROLE NOTHING SHOULD TRUST

JwtPayload has sub, email and role, and validate() returns it unchanged, so
request.user.role is available on every controller. All three guards
correctly ignore it and re-read. Nothing stops the next controller reaching
for it because it is conveniently to hand.

7.4 Facility.staff IS A MISLEADING NAME

The Prisma relation is called "FacilityStaff", but User.facilityId is a
single column carrying operators AND residents, so it returns both.
listFacilityMembers reads it once and partitions by role rather than
trusting the name. Renaming touches every consumer for no behavioural gain,
so it was left - but the name lies.

7.5 POST /incidents IS A SECOND CREATION DOOR

incidents.controller.ts calls create() directly, bypassing the orchestrator:
no journey session, no notifications. It DOES now route to a facility, since
the snapshot lives in the service. Either wire it properly or mark it
internal.

7.6 DEACTIVATING A FACILITY DOES NOT REVOKE ANYTHING

Facility.isActive gates PROVISIONING only. It deliberately does NOT hide the
incident queue, because incident creation does not consult it and residents
stay assigned - so filtering the read would leave live emergencies routed to
a facility whose operators cannot see them. Making deactivation mean
revocation needs an atomic workflow that also reassigns residents and
revokes operator access. It cannot be a filter in a list query.

7.7 EVERYTHING FROM ULTRA 33 SECTION 5 STILL STANDS

DND blocking SMS to Nigerian numbers, the journey session ACTIVE since
6 August, WhatsApp needing a WABA, email unconfigured, push reaching only
people who have OPA installed. None of it was touched.

DEPLOY ORDER IS AMENDED. Ultra 33's rule was written for a config change and

  MIGRATIONS FIRST, THEN CODE.

  migrate -> verify migrate status -> push -> workflow_dispatch -> verify

New code reads columns old schemas lack. Migrations are additive and the old
code ignores the new columns, so a widened schema is safe under running
code. The reverse is not.

VERIFY BY EXERCISING A REAL PATH. /health returns 200 on a broken build.
POST /auth/login with a bad password and expect 401.

RUN EACH GATE SEPARATELY. Piping jest through Select-String makes PowerShell
treat node's stderr as a terminating error and swallows the exit code.

STATE PREDICTED COUNTS AS PREDICTIONS. Confirm them from the run. One
prediction was wrong this session - 404 against 405 - because a test was
written and not counted. The discrepancy is the point of predicting.
