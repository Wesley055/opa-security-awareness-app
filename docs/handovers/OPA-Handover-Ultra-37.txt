20.2  GAP-01B — THE DIAGNOSIS
--------------------------------------------------------------------------------

THE DEFECT

  journey-queue-store.ts had:

      async listOldest(limit: number): Promise<StoredJourneyFix[]>
        SELECT ... FROM journey_queue ORDER BY queue_id ASC LIMIT ?

  No session filter. Rows were written per-session (enqueue carries
  sessionId) but read globally, oldest first. flush() then posted whatever
  came back under the CURRENT session id.

  Rows outlive the session that captured them. The wire carries ONE sessionId
  for the whole request. So any batch containing a row from an older session
  was mislabelled, and the server correctly rejected it.

THE PROOF — Azure API logs, /journey/fixes

  BadRequestException: recordedAt precedes the session:
    2026-08-11T05:38:06.426Z

  Same message, same timestamp, on 13 Aug, 14 Aug (six times), 15 Aug,
  16 Aug, and again at 18 Aug 23:38 UTC. ONE fix recorded on 11 August sat at
  the head of the queue and was replayed under every later session for six
  days.

  Before that row existed, the same defect produced:
    ConflictException: Journey session has ended    (9 Aug)

  So the defect predates the 11 August row. It is not a data problem.

WHY IT NEVER SELF-CLEARED

  flush() retains every row on rejection — correctly, per ADR-014 section 11.
  Emergency evidence is never discarded on a server refusal. Combined with an
  unfiltered read, one foreign row at the head halts the drain PERMANENTLY.
  That is not a bug in the retention policy. The retention policy is right.
  The read was wrong.

WHY IT SURVIVED FIVE HANDOVERS

  1. Every fixture in journey-tracker.spec.ts used 'session-1' for BOTH the
     stored row and the tracker's active session. replaySession === forSession
     in every test. The distinction the defect turns on was never exercised.
  2. flushForTests() calls flush() directly, bypassing the timer.
  3. After 16 August the SQLite failure (GAP-01A) began throwing before
     listOldest could reach the network, so the 400s stopped appearing in the
     API logs. The second bug MASKED the first.

20.3  GAP-01B — WHAT WAS BUILT
--------------------------------------------------------------------------------

GAP-01B-01 — nextReplaySession(currentSessionId, skippedSessionIds)
  feb4787

  Selects the ONE session the next replay cycle may drain.
    current session has rows  → return it
    otherwise                 → oldest queued session not in the skip set
    nothing eligible          → null

  The current session is checked BEFORE the skip set and is NEVER skipped. A
  faulted live session retries every tick by design; a faulted historical
  session yields the tick. That asymmetry is the whole point — it is what
  stops a dead session starving a live emergency.

  Two bounded queries, not one clever one. NOT IN () is a syntax error in
  SQLite, so the empty-skip-set case is a separate statement.

GAP-01B-02 — listOldestForSession / deleteAcknowledgedForSession
  4bef27e

  listOldestForSession(sessionId, limit)
    Adds WHERE session_id = ?. Parameters bind [sessionId, limit] — REVERSED
    BINDINGS ARE THE SILENT FAILURE: SQLite binds the limit to session_id,
    matches nothing, returns an empty batch, and the drain looks perfectly
    healthy while transmitting nothing.

  deleteAcknowledgedForSession(sessionId, keys)
    DELETE ... WHERE session_id = ? AND idempotency_key IN (...)
    Makes the shortfall count structurally session-safe rather than relying on
    the key format (sessionId:ms:sequence) never colliding.

  Both are NEW NAMES, not changed signatures. listOldest and
  deleteAcknowledged remain, still tested, because flush() still called them
  at that point. They lost their last caller in a761dbd and are now dead code
  — see 20.8.

GAP-01B-03 — the flush() rewrite
  a761dbd

  flush() now:
    1. asks nextReplaySession() which session may drain this tick
    2. reads a HOMOGENEOUS batch for that session
    3. POSTs under THE STORED SESSION, never the current one
    4. deletes only that session's acknowledged keys
    5. faults THAT SESSION on rejection

  ONE session per invocation. Never a loop — a 15s tick that drains every
  eligible session puts an unbounded number of POSTs and deletes inside one
  callback, which is trap #225 relocated into the replay path.

  New module state in journey-tracker.ts:
    historicalReplayFaults: Map<string, ReplayFault>
    skippedReplaySessions: Set<string>
    hasAnyReplayFault()      — used by the enqueue depth bound and the trim
    recordReplayFault()      — active → replayFault; historical → skip set

  RUNTIME-ONLY CONTAINMENT. Both clear on process restart. That is
  deliberate: HTTP 404 is documented as INDETERMINATE and must not become a
  permanent verdict. It is NOT durable quarantine and does not replace it.

20.6  FIVE REFUTED HYPOTHESES — DO NOT RE-DERIVE
--------------------------------------------------------------------------------

All five were raised during this session and all five are dead. Each is
recorded with the evidence that killed it.

1. "The flush timer never starts when background capture succeeds."
   REFUTED. journey-tracker.ts line 621: flushTimer = setInterval sits at
   function level, AFTER the if (!backgroundStarted) block closes at 613.
   Background capture succeeding does not skip the timer.

2. "flushing = true is never reset, so flush is one-shot."
   REFUTED. finally block at line 500, unconditional: flushing = false.

3. "openDatabaseAsync leaks a native handle per background delivery."
   REFUTED. expo-sqlite NativeDatabase.d.ts line 36: useNewConnection
   defaults FALSE, and the native layer caches connections BY DATABASE NAME.
   openDatabaseAsync returns a JS wrapper over a SHARED native connection.
   There is no handle leak. Consequence: calling closeAsync() in the
   background path would close the connection the FOREGROUND is using. That
   "fix" would have made things worse.

4. "withExclusiveTransactionAsync leaks its useNewConnection:true connection."
   REFUTED. SQLiteDatabase.js lines 165–167:
       finally { await transaction.closeAsync(); }
   Always closed, on both the commit and rollback paths.

5. "The headless TaskManager context cannot prepare statements."
   REFUTED BY DEVICE. At 09:38:04 the FOREGROUND flush failed with the same
   prepareAsync rejection, one second after the last successful background
   write and nine seconds before the next background failure. The failure is
   PROCESS-WIDE, not context-specific.

Two commits (a1a7b7c, f0adacb) were built on hypotheses 3 and 4. They are
DEFENSIBLE IMPROVEMENTS — one open and one transaction per delivery instead
of one per position, which measurably matters for the 52- and 42-position
batches later observed — but NEITHER TOUCHED THE CAUSE. The failure is
bit-for-bit identical before and after.

20.7  THE ONE REMAINING CANDIDATE (UNTESTED)
--------------------------------------------------------------------------------

State it as a hypothesis, not a finding. Four have already died.

  The only SQLite work in the second before every observed collapse is an
  enqueueBatch, whose final act is
      withExclusiveTransactionAsync → finally → transaction.closeAsync()
  on a connection opened with useNewConnection: true.

  Closing that connection while the shared cached connection has statements
  outstanding would plausibly produce exactly what is observed: database
  handle alive, statement preparation broken process-wide, permanently.

  It is consistent with all four device runs. It is not proven.

THE CHEAP EXPERIMENT THAT DISTINGUISHES IT
  Build a variant where enqueueBatch writes via plain runAsync — no
  withExclusiveTransactionAsync. count() and getCaptureSequence() already
  read without a transaction, so the pattern exists in the file.
    survives a long locked run  → the exclusive transaction is the cause
    fails identically           → the transaction is exonerated, and the
                                  answer is upstream in expo-sqlite
  Cost: atomicity between the inserts and the sequence marker, which the
  idempotency_key UNIQUE constraint largely covers anyway. This is a
  DIAGNOSTIC build, not a shipping design.

WHAT IS STILL UNINSTRUMENTED
  The transaction boundary itself. BGSQL 8 and 9 bracket the whole
  enqueueBatch call. Nothing shows whether the transaction CLOSED on the last
  successful write before the collapse. Markers immediately before
  withExclusiveTransactionAsync, immediately inside it, and immediately after
  it returns would settle it.

CURRENT DIAGNOSTIC INSTRUMENTATION (uncommitted, on top of f0adacb)
  BGSQL 1–9      journey-background-task.ts, the whole capture path
  BOOTSQL A/B    around isBootstrapped()'s getFirstAsync
  FLUSHSQL A/B   around nextReplaySession() in flush()
  plus a `throw err` added to captureBackgroundBatch's catch so the failure
  reaches TaskManager instead of being swallowed.

  THE `throw err` IS DIAGNOSTIC BEHAVIOUR AND MUST BE REMOVED BEFORE
  SHIPPING, along with every console.log marker. Production logs the batch
  failure and returns.

  Passes 83/83 and tsc. Do NOT commit it. EAS packages the working tree, so
  a diagnostic APK does not require a commit.

GAP-01A  — cause unknown. Blocks everything downstream. See 20.7.

GAP-01B-04 — ReplayHealth
  trackerDebugState still exposes a single replayFault, which NOW MEANS THE
  ACTIVE SESSION'S FAULT ONLY. Historical faults live in module state and are
  invisible to the Command Center. That is a real observability gap. Target
  shape:
      type ReplayHealth = {
        activeSessionFault: ReplayFault | null;
        historicalFaults: Record<string, ReplayFault>;
      }
  Note trackerDebugState is asserted with toEqual in several tracker tests,
  so changing the return type breaks them loudly. Good.

Durable quarantine and reconciliation
  The skip set is runtime-only. Sessions that fail repeatedly across launches
  are never reconciled. Needs a schema change — which should NOT happen while
  the SQLite lifecycle is unstable.

Eviction policy
  trimToDepth is global. Quarantined historical rows can eventually consume
  the live incident's budget. Proposed direction is separate reserves
  (live / historical-recoverable / quarantined) — this changes
  evidence-retention semantics and needs an explicit ADR amendment, not a
  silent reversal of "oldest first".

Tests B and C (specified, not written)
  B — historical session 409s; the next tick must reach the live session
      rather than retrying the dead one.
  C — after a 2xx on session-old, deleteAcknowledgedForSession is called with
      'session-old' and only that batch's keys.
  Both depend on whether the spec's beforeEach calls
  resetTrackerStateForTests(), since historicalReplayFaults and
  skippedReplaySessions are module state.

SQLite-backed integration test
  Insert across three sessions, assert real cross-session isolation and real
  ORDER BY behaviour, and confirm ASC→DESC then fails. Until this exists,
  ordering and filtering are implemented but unproven.

Dead code
  listOldest(limit) and deleteAcknowledged(keys) lost their last caller in
  a761dbd. Removing them is a separate commit.

versionCode
  Still 1 on every build. Play requires monotonic increments for the internal
  testing track. Bump it per build in app.json.

20.9  NEW TRAPS
--------------------------------------------------------------------------------

#226  A UTF-8 BOM written into a commit-message file lands in the SUBJECT
      LINE. Commit 5d1fb44's subject does not start with 'd'; any
      grep '^docs' over git log --oneline silently skips it. Use git commit
      -m, or write the file as UTF8 WITHOUT BOM.

#227  LINE ENDINGS DIFFER FILE-TO-FILE INSIDE ONE REPO. An installer that
      rewrites a file with LF leaves it LF while its untouched neighbours stay
      CRLF (autocrlf=true). An anchor then matches one file and fails against
      another. THE FAILURE PATTERN IS THE DIAGNOSIS: single-line anchors match,
      every multi-line anchor returns zero. Normalize BOTH needle and haystack
      to LF before matching; never infer the convention from one file.

#228  A .ps1 downloaded through a browser arrives CRLF regardless of how it
      was written. Combined with #227 this produced a 15-of-17 anchor failure
      that looked like a content mismatch and was not.

#229  Inside a PowerShell hashtable literal, the comma in
      `-replace "a", "b"` is parsed as an ENTRY SEPARATOR and the literal
      fails to parse. Assign before building the object, or use .Replace().

#230  A PowerShell here-string does not preserve the blank line before its
      closing delimiter. Anchor-based method insertion therefore lands the new
      member FLUSH against the following one. Put the separator inside the
      replacement string explicitly. This happened twice and needed two manual
      fixes.

#231  A browser that has seen the filename before saves as "name (1).ps1".
      Resolve the path with Get-ChildItem rather than typing it.

#232  MOCKED SQLITE TESTS CANNOT PROVE DEVICE BEHAVIOUR. Already recorded in
      journey-queue-store.spec.ts and re-confirmed this session: 83/83 green
      while every background write failed on hardware. A test count is not
      evidence. Only a device log is.

#233  MEASUREMENTS TAKEN AT DIFFERENT PROCESS AGES CONTRADICT EACH OTHER.
      The durable queue's observable state was a function of process age, not
      of the code under test. Every device measurement MUST be preceded by
      `adb shell am force-stop` and `adb logcat -c`, and the process age must
      be recorded alongside the result. The one run that followed this
      protocol produced the only coherent story of the night.
