### 9b.2 THE FALSE REGRESSION - the reasoning worth keeping

**Ultra 12 concluded the two tracker fixes had made things STRICTLY WORSE and
recommended in three places that they not be committed. That was wrong.**

Evidence it had: after the fixes, two activations fourteen minutes apart produced

**Two facts settled it with no device time, both readable from artifacts that
already existed:**

1. **`trackingStartedAtMs` is initialised to `0`.** So `ms < trackingStartedAtMs`

   `startTracking()` ran to completion.** This turns two competing readings of

2. **`acquireSession()` sits BELOW `if (running) return`.** A full start always

**The API log already contained the answer:** `/journey/sessions` appears

activations returned 201 with no session POST.

**Verdict: the diff never ran.** Stronger: Metro re-evaluates an edited module,
which would have reset `running` and produced a session POST. None appeared. **So
the phone ran the PRE-FIX bundle throughout. Nothing was ever compared to
anything.** Trap #80.

Two independent silencers, **neither caused by the diff**: the `if (running)`
no-op, and the surviving subscription still carrying `distanceInterval: 25`.

**THE GENERAL LESSON, now the fifth instance:** a fix framed too narrowly (#73);
a correct write failing a wrong assertion (#76); a well-reasoned fix that looked
worse; a handover recommending reverting a correct commit; **and a broken glob

### 9b.3 THE BOOT POLICY - AND IT HAS TWO CAUSES, NOT ONE

**Cause 1: the provider validator.** `ProviderConfidenceValidator.onModuleInit()`
filters six mock-capable providers and **THROWS** unless
`OPA_ALLOW_MOCK_PROVIDERS === 'true'` (strict equality). Six of seven providers
are `MOCK`. `.env` sets it locally; **Azure never had it.** Observed twice in
real Azure Log Stream.

**This is not a bug.** Opt-IN, deliberately not `NODE_ENV`-derived, so
**forgetting it fails CLOSED.** A mock geocoder returning a plausible invented
address could send a responder to the wrong place.

**Two dead ends, both eliminated this session:**
- **Response gating alone does NOT satisfy the validator.** It is a boot-time
  check on *registered providers*, not on response shape. **This answers q10.**
- **Conditional registration does NOT work.** The six providers are **concrete
  constructor parameters**; omit one from the module array and Nest fails DI
  resolution - a different boot failure, not a validator seeing five.

**THE FINDING THAT DECIDES IT.** `incident-orchestrator.service.ts:86` awaits
`buildLocationIntelligence` on the **SOS activation path** (injected at `:37`;
module imported at `app.module.ts:48` and
`incident-orchestrator.module.ts:19`). **The module cannot be unregistered - the
orchestrator would not resolve.** This is why `Omitted from response due to mock
providers` fired on **every** activation in the device logs.

**So: the module must stay registered; the service already nulls every
mock-backed section per provider independently; nothing fabricated reaches a
user; and the ONLY blocker from this cause is the `throw`.**

**PR 1 (`6188e63`) removed everything else in the way** - three duplicate copies
of the mock predicate collapsed into one, and a widened
`{ dataConfidence: string }` narrowed to `IntelligenceProvider`.

**Cause 2, NEW AND NOT PREVIOUSLY RECORDED: `evidence.service.ts` calls
`config.getOrThrow` for `AZURE_STORAGE_CONNECTION_STRING` and
`AZURE_STORAGE_CONTAINER` IN ITS CONSTRUCTOR**, and `EvidenceModule` is
registered at `app.module.ts:54`. **A missing variable stops boot BEFORE the
provider validator is reached.** It boots locally, so `.env` has both. **Azure is
unverified.**

**Check Azure app settings for both variables before assuming the boot fix is a
single decision.** Cheap, and it may be the real first blocker.

**ADR-012 - both positions, for the validator question:**

**Position A - keep the `throw`.** It is the backstop for a mistake nobody has
made yet: a seventh provider added without a matching null check. The service's
omission is **six hand-written checks in a 148-line method**, not a loop. Remove
the throw and the only protection is that a long method was maintained correctly
forever, with nothing re-verifying it. Today a missed null fails at boot, loudly,
naming the provider.

**Position B - permit boot.** The strict gate blocks deployment for a condition
the service already handles correctly. A guard that prevents shipping a working
product is over-strict, and the error message itself names response gating as a
legitimate remedy.

**A synthesis worth considering rather than a third mode.** A separate flag
creates a second operational mode that must be tested forever. But the state
wanted in production **is** "mock providers registered, outputs omitted, boot
permitted" - one mode, not two. `OPA_ALLOW_MOCK_PROVIDERS` is named for
permission and reads as recklessness, which is why three documents ban it in
Azure. **Its name and message are wrong for that state; its mechanism is not.** A
rename plus a rewritten message keeps the throw for the case it exists to catch
and needs no new variable.

**What must NOT change: the error message.** It names the providers, explains the
danger, offers three remedies, and refuses to guess. **It is the clearest writing
in the codebase.**

**Also keep:** the test pinning that `TRUE`, `True`, `1`, `yes`, `on`, `false`
and `''` all **still fail** the strict `=== 'true'` comparison.

### 9b.5 EVIDENCE ARCHITECTURE - DECISIONS TAKEN, ADR-013 OWED

Reached across a review exchange this session. **Write these up; the reasoning is
what will otherwise be lost.**

**1. Priority ordering, and evidence must never delay location.**
```
location -> SOS/status messages -> telemetry -> audio -> photos -> video
```
A 200-fix batch is a few KB; thirty seconds of video is several MB. **On a weak
connection during an emergency, video uploads would starve the location updates
- degrading a proven capability to add an unproven one.**

**Implementation note:** location and evidence go to **different endpoints** -
`POST /journey/fixes` versus a multipart blob upload with a **50MB in-memory
buffer cap**. So the priority queue is client-side scheduling across two very
different transports, not one queue.

**2. AUDIO ABOVE PHOTOS.** Revised during the session and the argument is
decisive: a phone in a purse, pocket, face-down or in a car console produces
twenty unusable photos, but a microphone in the same purse still captures
speech. **Audio does not depend on where the camera points.**

**3. THE BINDING CONSTRAINT ON AUDIO IS BYSTANDER CONSENT, NOT USER CONSENT.**
The user can consent to being recorded. **The user CANNOT consent on behalf of
the shopkeeper, passer-by or colleague whose voice ends up in the file.** That is
why audio is legally harder than location: location records where *you* were;
audio records what *other people said*. Jurisdictions requiring all-party consent
are not satisfied by the app owner opting in during setup.

**Correct framing: silent to the user's attacker, documented in the legal basis.**
Silent activation is fine. What cannot be silent is the record of *why* capture
was lawful. **A question for counsel about a specific jurisdiction, not a design
toggle** - and the one item that genuinely blocks on NDPA rather than merely
coinciding with it.

**Also: an audio recording is only evidence if it is admissible.** A file
captured without a defensible consent basis may be worse than nothing, because it
invites a challenge to the whole record - **including the location half that
currently IS clean.**

**4. TWO INTEGRITY MECHANISMS, KEPT SEPARATE.** Location fixes have a **hash
chain**, which proves nothing was REMOVED. Evidence has **per-object sha256**,
which proves an individual file was not altered. **A chain is strictly stronger.**
`GPS_LOG` exists as an `EvidenceType` and **folding location into per-object
evidence would WEAKEN it.** Right model: two mechanisms, one timeline referencing
both. **Decide explicitly, because `GPS_LOG` existing invites the weak way.**

**5. AI SUMMARIES ARE NOT EVIDENCE OBJECTS.** A captured artifact and a derived
interpretation cannot carry the same evidentiary status. If a summary sits in the
same structure with the same hash and the same timeline position as a recording,
equal provenance is implied - and **the first competent challenge attacks the
summary and discredits everything adjacent to it.** Derived material belongs in
a **separate, clearly-labelled layer that REFERENCES evidence rather than being
evidence.** Same reason chain of custody distinguishes the sample from the lab's
opinion about it.

**6. DEVELOPMENT AND DEPLOYMENT ARE SEPARABLE.** The pipeline, APIs, storage,
upload queues and timeline model can be built while capture release waits on
regulatory work. **And most of that pipeline already exists** - see 9b.4. That
argument is stronger than when it was made.

**7. RESPONSE COORDINATION - DEFERRED, NOT REJECTED.**

Decided this session: **OPA is the evidentiary layer for now.** Coordination is a
real future product; it is not now.

**Why deferred rather than rejected.** Independence is the only structurally
uncopyable advantage today - **a responder cannot produce neutral evidence about
their own response.** Coordinating makes OPA a party to what it attests. That
cost is real but not permanent.

**Critically: the hash chain does NOT rescue this.** Cryptographic integrity
proves the record was not altered after the fact. It says nothing about whether
the party who wrote it had an interest in what it said. **Tamper-evidence is not
independence.**

**The boundary while deferred: VIEWER, NEVER CONSOLE.** Incident list, live
position, report retrieval - yes. Responder assignment, status tracking,
escalation management - no. **Stated explicitly because a viewer drifts into a
console one reasonable request at a time, and drift is how this decision would
get reversed without anyone deciding.**

**Where the line actually falls:** notifying contacts is *alerting*. Giving a
responder scoped live location is *providing information*. Recording that a
responder acknowledged at 14:02:40 is *observing someone else's action* - which
is why acknowledgement is so valuable: **it proves response time without OPA
participating in the response.** Coordination starts at *deciding and directing*.

**What would justify revisiting:** a partnership attempt with a response operator
that fails or is declined; institutional buyers requiring dispatch as a condition
of purchase; a funded route to actual response capability; or OPA's record
becoming commodity rather than differentiator.

**What must NOT happen while deferred:** coordination features shipped
incrementally under other names. **If revisited, it is revisited as a decision,
with this ADR superseded.**

**Note: keeping architectural separation costs almost nothing and preserves both
paths.** A record layer partners can write into is also one OPA's own future
console could write into. Deferring requires not building the console yet, not
building anything differently.

**The honest counter-argument, recorded:** coordination is where recurring
revenue and stickiness usually live, integrated products often beat modular ones,
and a pure recorder depends on someone else's distribution. **This is a bet, not
a theorem.**

> Correct sequence: pilot -> users -> reliability -> partners ask -> API.
> Building an SDK or public API now solves a problem nobody has asked to have
> solved. OPA currently has no pilot, no revenue, no public API, no third-party
> auth model, no docs and no operational history.

### 9b.7 THE DEVICE-DARK ANALYSIS - four states, one recoverable

If a phone has location revoked, is in airplane mode, is force-killed or powered
off, **no software safety app can transmit from it.** An OS and physics limit,
not an OPA gap, and it applies equally to every phone-based competitor and to the
OS vendors' own features.

| State | Capture | Transmit | Trail |
|---|---|---|---|
| Location revoked | no | yes | ends |
| **Airplane mode** | **yes - GNSS is receive-only** | no | **delayed, not lost** |
| Force-killed | no | no | ends |
| Powered off | no | no | ends |

**Airplane mode is materially different and it is the case 9c changes.** A phone
in airplane mode continues producing position fixes. **With a durable queue,
every fix captured during the dark period flushes on reconnect** - *"here is
where the phone travelled during the two hours it appeared dark."* Qualitatively
stronger than a last-known location, and exactly what item 10's airplane-mode
test exercises. **It depends on background capture too, since the app must
survive being backgrounded.**

**Honestly preserved in the unrecoverable cases:** a trail rather than a snapshot
(10s cadence); **origin coordinates immutable** (ADR-005); a tamper-evident chain.

**THE GAP: going dark is NOT an attested event.** `SILENT` is derived at read
time from fix age - **not persisted, not hash-chained.** So *"the device went
dark at 14:53:50"* is an inference from absence, not a fact in the record.
**Making it attestable is 14b, and this is the strongest single argument for it.**

**Being honest about all this is a commercial asset, not a weakness to hide.** An
institutional buyer finds the limit anyway, and trusts whoever named it first.

**The one genuine software-only mitigation is SILENT ACTIVATION** - it does not
fix a physical problem, it reduces how often the worst case is reached, because
an activation that does not announce itself is less likely to be noticed and shut
down before the alert has gone out. **By the inclusion test it is CORE.**
