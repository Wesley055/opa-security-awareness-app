### 2.1 ULTRA 23 SECTION 4 - RETRIGGER AGAINST A TERMINAL SESSION [D]

DECISION: option (a). A retrigger against an incident whose linked session
is missing or ENDED resolves an open session rather than appending to the
terminal one.

Shipped in 73d829e, entirely inside recordRetriggerFix in
journey-session.service.ts. THE ORCHESTRATOR'S LOGIC WAS NOT CHANGED - only
its call-site comment, which was wrong. All lifecycle policy stays in the
Journey module.

[D] THE GUARD IS WRITTEN ON status === 'ENDED', NOT ON AN ALLOWLIST OF OPEN
STATUSES. An allowlist's failure mode when a sixth status appears is
"resolve a fresh session on every retrigger, silently, on the emergency
path." The ENDED guard's failure mode is "reuse a session it perhaps should
not." The second is the safer default.

[D] A MISSING ROW IS FOLDED IN WITH ENDED rather than throwing. The FK is
ON DELETE SET NULL so it should be unreachable, and an SOS must not fail on
a stale pointer.

[D] THE ENDED SESSION IS NOT REOPENED. status, endedAt and endedReason are
untouched. USER_ENDED remains terminal for what it terminated; the retrigger
starts new telemetry rather than resurrecting old.

[M] WHY (a) IS POSSIBLE AT ALL: the partial unique index
journey_session_one_active_per_user covers only STARTED and ACTIVE, so the
ended session has already vacated the per-user slot and resolveForActivation
can create a successor. Had that index covered ENDED, option (a) would not
exist. The July migration decided this before anyone asked the question.

[D] ADMIN_ENDED IS ROUTED AROUND BY THE WIDE GUARD. There is no admin
surface, so this is recorded rather than solved. Whoever builds one must
decide whether a retrigger may bypass an administrative kill.

### 2.2 THE SECOND, UNCOUNTED FIX - INCIDENT RELINK [M]

incident-orchestrator.service.ts's call site has always stated that
recordRetriggerFix "resolves and links a session of its own when
incident.journeySessionId is null." Measured: it resolved. It never linked.

CONSEQUENCE, LIVE IN SHIPPED CODE UNTIL 73d829e: a retrigger on an incident
with a null journeySessionId wrote the fix to a resolved session while the
incident still pointed nowhere. public-tracking.service.ts selects
incident -> journeySession -> newest fix, so the family's tracking link
rendered NO SESSION during an active retriggered SOS.

FIXED: the incident FK is now updated whenever the selected session differs
from the incident's current link, inside the same transaction. This covers
both the null case and the ENDED case with one branch.

[M] PRECEDENT, NOT INVENTION: incident-orchestrator.service.ts already
writes { journeySessionId } unconditionally on the create path, and
resolveForActivation may REUSE a session there, so several incidents
pointing at one session is already tolerated.

### 2.3 WHAT PUBLIC TRACKING SHOWS, MEASURED [M]

public-tracking.service.ts selects the linked session and, from it, fixes
with take: 1 ordered by receivedAt desc, sequence desc. IT RETURNS ONE FIX,
NOT A TRAIL.

Therefore relinking does NOT lose displayed history, because none was being
served through that query. What is true and was written into ADR-014
section 10:
  - live tracking resumes on the newly linked session;
  - fixes on the previous session remain stored, and are not modified or
    deleted (JourneyLocationFix is ON DELETE RESTRICT);
  - they are not reachable through this current-session query;
  - whether a client renders that as a discontinuity depends on the client.

[R] DO NOT WRITE "continuity solved" OR "full history preserved" ANYWHERE.
Neither is true. Representing multiple journey segments per incident is a
separate design decision - see section 9.2.

### 3.3 THE MUTATION HARNESS - NOW THE STANDARD METHOD [R]

Proven on three independent files this session. The pattern:

  1. REFUSE TO RUN unless git status --porcelain is empty.
  2. Back up the target file's raw bytes before touching it.
  3. Assert the mutation anchor matches EXACTLY ONCE; refuse otherwise.
  4. Apply, print the diff, run the suite, capture the exit code.
  5. RESTORE IN A finally BLOCK, so a crash mid-run cannot leave a
     mutated file on disk.
  6. Re-run the suite after restore and capture that exit code too.
  7. AFTER the finally block, assert: mutation exit != 0, restore exit == 0,
     porcelain == 0. Throw on any of them.

Step 7 is what converts "I looked at the output" into an exit code. Step 5
is what makes it safe to run on a file that is already committed.

  - MAX_QUEUED_FIXES = 600, overflow slices from the FRONT (oldest dropped).
  - FLUSH_INTERVAL_MS 15000, MAX_BATCH 200, TIME_INTERVAL_MS 10000.
  - recordedAt is CAPTURE time, not send time.
  - Nothing is removed from the queue until a 2xx returns (trap 74).
  - captureSeq, trackingStartedAtMs and sessionId are also module scope and

[M] THREE THINGS THAT SHAPE 9c MORE THAN THE STORAGE CHOICE:

  1. THE IDEMPOTENCY KEY EMBEDS THE SESSION ID:
     `${sessionId}:${ms}:${captureSeq}`. A persisted fix therefore carries a
     key scoped to a session that may be ENDED by the time the app
     restarts. Re-tagging changes the key, which changes the dedupe
     identity against @@unique([journeySessionId, idempotencyKey]). THIS IS
     ADR-014 SECTION 4's REACQUIRE PROBLEM, arriving through the client.

  2. captureSeq RESETS TO 0 ON RESTART. Same session, same millisecond, and
     a restored fix can collide with a new one. Persist captureSeq with the
     queue.

  3. flush() TAKES forSession EXPLICITLY BUT THE QUEUE HAS NO SESSION
     COLUMN. Harmless while the queue dies with the process; once it
     persists, fixes from two sessions become indistinguishable. Store the
     session per fix, or scope the store per session.

[M] SECTION 6 OF ADR-014 IS DECISIVE ON ORDERING AND MUST NOT BE
RE-LITIGATED. Oldest-first flushing is an explicit invariant because
893d65a's receivedAt DESC, sequence DESC ordering is correct ONLY IF the
tracker flushes in capture order. Retrying an old batch after newer ones
succeed makes the newest receivedAt carry the oldest recordedAt, and the
tracking page presents a stale position as current - to a family member
during an emergency. Head-of-line blocking is an ACCEPTED consequence:
during it the page renders silent, indistinguishable from signal loss.
"Skip the held item" is explicitly rejected.

[M] THE RETENTION CEILING REMAINS AN UNDECIDED EXPLICIT PARAMETER. ADR-014
section 5 bounds it (600 fixes at 10s is ~100 minutes of depth; a ceiling
shorter than a plausible offline window defeats 9c) but does not pick a
value, and warns it must not be set implicitly by an eviction policy
written later. IT IS AN AGE CEILING, NOT A DEPTH CEILING - depth is already
bounded. This is a product judgement, not an engineering one.

[M] NO STORAGE DEPENDENCY IS INSTALLED. apps/mobile-app/package.json has
neither expo-sqlite nor @react-native-async-storage/async-storage.
journey-tracker.ts line 30 says 9c "needs a new dependency"; ADR-014 does
