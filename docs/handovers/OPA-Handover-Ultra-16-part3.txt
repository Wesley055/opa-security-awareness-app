## 17. Known issues - document, do not fix inside a milestone

### 1. Timeline events written outside the transaction - STILL OPEN

The orchestrator's `$transaction` closes at **line 326** (NOT 274 - Ultra 15's
figure had drifted by 52); every `recordEvent` fires after it, at **336, 376,
388, 408**. A crash between commit and 336 leaves an incremented `retriggerCount`
with no event recording where the person was.

**`96cf7de` did NOT touch this and correctly so - the lock addresses
concurrency, not atomicity.**

**NEW AND IMPORTANT: fixing this is now harder than it was.** Making the write
atomic means passing the caller's `tx` into `recordEvent` instead of it opening
its own transaction. **But `recordEvent` now takes an advisory lock, so an outer
transaction holding a lock that the inner one waits on becomes a deadlock rather
than today's harmless nesting.** Every caller must be re-verified first.
**Currently verified safe: `evidence.service.ts` has no `$transaction` at all,
and the orchestrator's four calls are all after its own commit.**

**This is the positive case for `4d544a9` putting the journey fix INSIDE the
transaction: the position survives that window even though the audit event does
not.**

### 2. `recordEvent` sequence race - FIXED AND PROVEN

**`96cf7de`** added `pg_advisory_xact_lock(3, hashtext(incidentId))` as the first
statement inside the existing transaction. **`3da28b7`** proved it serialises,
with a control case ruling out connection serialisation.

**Retained as a fact, not an issue:** the chain itself pre-existed both commits
and was recorded in Ultra 15 as absent.

### 13. NOTHING STOPS THE TRACKER WHEN LEAVING THE SOS SCREEN

`stopTracking()` is called from exactly one place: `_layout.tsx`, on
`isAuthenticated` going false. **Navigating back does not stop it.** So `running`
stays true and a second activation no-ops, keeping the FIRST session's
`sessionId`.

**CONFIRMED TWICE.** After one clean run the tracker was still flushing **nine
minutes** past the end of the test.

**NEWLY LOAD-BEARING FOR ADR-014.** Because the client keeps the ended session's
id after supersession, every subsequent fix is addressed to an `ENDED` session
with `recordedAt >= endedAt`. **A naive "permanent rejection means delete" rule
would silently discard all of them while the app appeared to be tracking - in the
exact case that matters, since supersession happens when a NEW incident starts.**
See part 2 section 9b.9 refinement 1.

**`startTracking()` should probably detect a changed session and restart rather
than no-op.** **Interacts with q26, q28, ADR-014, and the evidence engine's stop
condition.**

**Operational consequence: force-close Expo Go after every device test.**
