2.1 THE SAME-ORIGIN BRIDGE (14A-1, 14A-2)

The browser never talks to the Azure API. Every operator call goes to a
Next route handler on opasafety.com which reads an httpOnly cookie and
forwards. THE API HOSTNAME AND THE TOKENS NEVER REACH CLIENT CODE.

  Tokens in httpOnly cookies, sameSite strict, secure in production.
  The login response body carries NO tokens - only whether it worked.
  localStorage was rejected: readable by any XSS on a page that renders
  resident names and live coordinates.

The pattern was already decided by lib/tracking.ts and was FOLLOWED, not
reinvented.

2.2 AUTOMATIC TOKEN REFRESH (14A-3)

The access token lives 15 minutes. Ultra 35 section 4.4 recorded hitting
that expiry three times manually in one session, each time mistaking it for
a failure. It is now invisible.

  GET  /api/operator/refresh   the page flow: /operator redirects here, it
                               rotates, sets cookies, redirects back
  POST /api/operator/refresh   for client polling - 14A-6 is its first
                               caller, written in 14A-3 with none

  A REJECTION AND AN OUTAGE ARE NOT THE SAME EVENT. 401 is authoritative -
  rotate() re-reads the user row and refuses unless the account exists, is
  isActive and is ACTIVE - so both cookies are cleared. A network failure
  or 5xx says nothing about the credential, so the cookies are PRESERVED.
  Clearing on an outage would destroy a valid 30-day refresh token because
  the API restarted.

  NO SINGLE-FLIGHT LOCK, AND THIS DEPENDS ON A BACKEND PROPERTY. rotate()
  performs no writes and nothing persists refresh-token state - there is no
  RefreshToken model in the schema, and IncidentAccessToken's revokedAt is
  for tracking links. IF SERVER-SIDE REVOCATION IS EVER ADDED, 14A-6's
  polling becomes a race and needs a guard.

  NO ROLE CHECK ON REFRESH. POST /auth/refresh returns tokens and no user
  object. Checking would mean decoding the token, which the three API
  guards deliberately refuse to do. Cost: an operator demoted mid-session
  keeps the console shell until their refresh token expires, seeing 403s.

  THE LOOP BREAKER IS THE LOGIN PAGE. Every failure lands on
  /operator/login WITH a reason parameter, and that page does not attempt
  rotation when a reason is present. Without it an outage bounces
  login -> refresh -> login forever.

2.4 FACILITY CONTEXT (14A-5)

no staff list.

2.5 THE OPERATOR QUEUE (14A-6)

  GET /operator/incidents   API, new controller, new guard

WHY A SECOND ROUTE when /facilities/:facilityId/incidents already worked:
the console would otherwise need the facility id in the browser to build
that URL. It could - FacilityOperatorGuard is the real boundary - but then
the browser holds a fact the server could supply, the bridge grows a query
parameter any authenticated caller can point anywhere, and a 403 path has
to exist for a reassigned operator. Deriving the facility from the token
removes all three at the cost of one controller.

  OperatorFacilityGuard BOTH AUTHORIZES AND ESTABLISHES CONTEXT. It reads
  the user row once and attaches request.operatorFacilityId. The
  alternative is reading the same row twice per 5-second poll.

  IT REFUSES AN ADMIN WITH NO FACILITY, and that is the one place it
  differs from FacilityOperatorGuard. That guard gives admins a cross-tenant
  override because a facility is named in the URL to override TO. Here there
  is nothing to override to.

  A METHOD-LEVEL GUARD ON FacilitiesController WOULD NOT HAVE WORKED. Nest
  guards are ADDITIVE, not overriding. The class-level FacilityOperatorGuard
  reads params.facilityId and would refuse a route that has none.

The website polls every 5 seconds, pauses while document.hidden, fetches
immediately on becoming visible, recovers a 401 with one rotation and one
retry, stops permanently on 403, and NEVER lets a failed poll empty the
queue - only a 200 replaces what is on screen.

2.6 INCIDENT DETAIL (14A-7)

  GET /incidents/:incidentId   API, new controller, IncidentAccessGuard

READ-ONLY, AND THAT IS A PRODUCT DECISION NOT AN OMISSION. No resolve, no
cancel, no acknowledge. incidents.service.ts states it: only the incident
owner may close an incident, because a Command Centre operator resolving
somebody else's emergency is a claim about the world made by an interested
party. A verify check in the installer fires if any write verb appears on
that controller.

The projection excludes metadata (dispatch plumbing), trustedContact
(untyped JSON that may carry a third party's details), facilityId, and
every relation. It includes journeySessionId, which nothing renders - 14A-8
needs it and this saves widening the projection later.

  THE PAGE SAYS "A location tracking session is linked", NOT "live". The
  projection returns the session id and not its state, and close() ends the
  session when an incident resolves - so a linked id on a closed incident
  belongs to a stream that has stopped.

  CANCELLED GETS ITS OWN BRANCH. close() writes resolvedAt only for
  RESOLVED, deliberately null for CANCELLED, because "an insurer, an auditor
  and a hospital risk committee will read 'this did not happen' and 'this
  happened and is over' very differently". Rendering "Resolved: -" would
  flatten that.

3.1 A RESOLVED INCIDENT STAYED ON SCREEN FOREVER

mergePages() fell through to a boundary path on an empty fresh page, took
POSITIVE_INFINITY as the boundary, and preserved every existing row. An

special-casing it. A first fix handled only fresh=[] and left the sibling
bug one row up - two loaded, one resolves, and the boundary path kept it.

3.2 THE DETAIL PAGE SHOWED THE WRONG INCIDENT

Navigating from /operator/incidents/A to /B keeps the same route pattern,
so React reconciled IncidentDetailView as the same element and did NOT
remount it. useState kept A's data and poll() kept calling A's endpoint.
The URL said B; the screen showed A.

FOUND BY NOTICING THAT A QUEUE ROW CREATED AT 11:58 OPENED A DETAIL PAGE
DATED 11:44. In an emergency console, clicking one emergency and being
shown another is close to the worst UI defect available.

Fixed with key={result.incident.id} on the client component.

THIS FIX IS REASONED, NOT OBSERVED. Reproducing it needs two clicks through
two different open incidents, which needs two simultaneously-open
incidents, which is impossible with one assigned resident - see 7.1.

3.3 SIGN OUT NAVIGATED TO RAW JSON

The logout route returned NextResponse.json({ ok: true }). A form POST
NAVIGATES to whatever the POST returns, so the operator landed on
{"ok":true} with no way back. It went unnoticed while the button sat in a
page body; 14A-4 moved it into the permanent shell where every operator
presses it at the end of every shift.

Fixed with a 303 redirect to /operator/login.

6. THE GOOGLE GEOCODING LICENSING GATE - 14A-8a IS BLOCKED
================================================================================

THE OPERATOR SEES COORDINATES, NOT AN ADDRESS, AND THAT IS CORRECT
BEHAVIOUR RATHER THAN A UI SHORTCUT.

GeocodingProvider is a MOCK. providerName is literally
'MockGeocodingProvider', dataConfidence is 'MOCK', and it returns
"12 Allen Avenue, Ikeja, Lagos" FOR ANY COORDINATE ON EARTH. So are the
places, hospital, police, routing and safe-place providers.

EmergencyIntelligenceService then nulls every geocoding-derived field
before it reaches a response, and ProviderConfidenceValidator refuses to
boot unless OPA_BOOT_WITH_SUPPRESSED_MOCKS=true. The validator's own
comment says why: "a responder could be sent to the wrong place."

So the suppression layer is working exactly as designed, and no amount of
website work produces an address.

There are TWO independent reasons the console shows coordinates:

  1. The geocoder is a mock, so the address is suppressed to null.
  2. Even when it is not null, the intelligence is computed for
     NOTIFICATIONS and discarded. Nothing writes it to Incident.address.
     incident-orchestrator.service.ts:153-159 documents the workaround -
     it sends a maps.google.com coordinate link instead.

FIX ONLY THE PROVIDER and the notification gets a real address while the
console still shows coordinates. FIX ONLY THE PERSISTENCE and you write
"12 Allen Avenue" onto every incident on earth. Both must land, provider
first.

6.1 THE DESIGN IS FULLY SPECIFIED AND PROVIDER-NEUTRAL

  GeocodingSweepService in emergency-intelligence (that module already owns
  the provider and the confidence boundary)
  @Cron every 60 seconds, batch 10, max 5 attempts, backoff 1m/5m/15m/1h
  Opt-in by OPA_GEOCODING_SWEEP_ENABLED, default false, so local dev and
  test never burn quota
  Retry state in Incident.metadata, never exposed to the console
  Writes only accepted addresses to the existing Incident.address column
  NEVER overwrites a non-null address - there is no addressSource
  provenance field, so overwriting would destroy information we cannot
  explain
  Coordinates always remain the fallback; OPA never fabricates an address

  IT MUST NOT RUN ON THE SOS PATH. A Google timeout, outage, quota error or
  DNS problem must never delay incident creation.

  IT MUST NOT RUN ON THE 5-SECOND POLL. That would geocode every row of
  every render.

  THE ACCEPTANCE FUNCTION MATTERS AS MUCH AS THE CALL. Parse
  address_components by semantic TYPE, never by array position - Google
  documents that the number of components varies, a component can change
  position, its type can change, and a component may be missing in a later
  response. Reject: empty formatted_address, plus-code-only results (a
  single result with no components, no formatted address and no types),
  and country/state/postal-only results. Distinguish ZERO_RESULTS (do not
  retry) from OVER_QUERY_LIMIT (retry later) from REQUEST_DENIED (never
  retry, alert).

6.2 WHAT IS BLOCKED, AND WHY

Google Maps Platform Service Specific Terms, last modified 10 June 2026,
non-EEA:

  6.3.2 permits INDEFINITE caching of latitude, longitude,
  formatted_address and structured address values "solely to support the
  direct, End User facing functionality of the Customer Application that
  initiated the request", where cached data "must be logically isolated to
  the specific End User it is associated with and must not be used across
  multiple End Users."

  6.2 states Geocoding API content must not be used in conjunction with a
  non-Google map.

OPA's operators are DIFFERENT PEOPLE from the resident who triggered the
SOS, and the planned post-incident report would send the address to an
insurer or an estate. Whether that is "used across multiple End Users" is
exactly what 6.3.2 does not settle - its examples are a weather app and a
photograph, both single-user.

And 6.2 couples the geocoder choice to the MAP choice: a Google-derived
address displayed beside a Leaflet or Mapbox map may breach it.

A SUPPORT CASE HAS BEEN RAISED asking both questions, in writing, by email,
citing the dated non-EEA terms and stating plainly that operators are
separate individuals.

  GOOGLE CLOUD SUPPORT CASE 74429063
  raised 15 August 2026, Technical issue, P4, opened against the
  OPA Safety Production project. Email, not chat, so there is a written
  record to cite.

  DO NOT TREAT A REPLY THAT LINKS BACK TO THE TERMS AS APPROVAL. Front-line
  support often cannot interpret contract language. Escalate to Maps
  Platform sales/contracts before committing the architecture.

  AN EARLIER READING OF THIS WAS WRONG AND IS RECORDED SO IT IS NOT
  REPEATED. Web searches returned ARCHIVED term versions and third-party
  blog commentary, all of which predate 6.3.2, and the conclusion drawn -
  "Google does not permit storing the formatted address" - was too broad.
  The current live terms page settled it. READ THE VENDOR'S LIVE DOCUMENT,
  NOT COMMENTARY ABOUT IT.

8.2 THE GUARD-ATTACHMENT SPEC CANNOT SEE METHOD-LEVEL GUARDS

controller-guard-attachment.spec.ts exists precisely to catch "a correct
guard on an undecorated controller is an unprotected endpoint with a
passing test suite". It reads Reflect.getMetadata(GUARDS_METADATA, target)
on the CLASS. A method-level @UseGuards is invisible to it.

Both new controllers this session use class-level guards, so both are
covered - but the suite's doc comment claims more than it proves. Trap
#191.

8.3 THERE IS NO .gitattributes AND THE REPO HAS MIXED LINE ENDINGS

Some files are CRLF from checkout, others LF because an installer rewrote
them. Some have a UTF-8 BOM, others do not.

THIS BROKE INSTALLER ANCHORS REPEATEDLY. A multi-line anchor written with
LF silently misses a CRLF file even though every line is present. Two
installers stripped a BOM and produced an unrelated line-1 diff that had to
be reverted by hand.

Adding "* text=auto" would prevent the next person seeing spurious
whole-file diffs. Every installer written after this discovery detects the
target file's own line ending and BOM and preserves both.

8.4 .next GOES STALE AFTER A BUILD AND GIVES A PHANTOM 404

Running npm run build while a dev server is live can leave the dev route
table inconsistent. /operator returned 404 while the build listed all 21
routes and the files were present on disk.

THIS COST DIAGNOSIS TIME FOUR SEPARATE TIMES. The fix is always:

  Ctrl+C; Remove-Item -Recurse -Force .next; npm run dev

8.5 TRAP #171 FIRED FOUR MORE TIMES, ALL SELF-INFLICTED

A verify check that greps for a token appearing legitimately elsewhere in
the same file will fire falsely. Four installers failed on exactly this:

  'getSessionState'  matched the doc comment explaining why the guard
                     lives in the page and not the layout
  'email'            matched "No email, no phone number, no token"
  'isVerified'       matched "isVerified is available and NOT shown"
  'Date.now()'       matched "AGE IS COMPUTED AGAINST serverTime, NOT
                     Date.now()"

Every one was a correct file failed by its own prose. The lesson is not
"remember the trap" - the warning was written in the header of the very
installers that then violated it. It is that a grep over a file which
documents its own decisions is inherently prone to this, and checks must be
written against SYNTAX from the start: `email:` not `email`,
`await getSessionState(` not `getSessionState`.

10. THINGS DISCOVERED THAT ARE NOT BUGS

10.1 ONE RESIDENT, ONE OPEN INCIDENT

The mobile app holds the resident in the emergency-activated state until
they press "I'm safe" or cancel as a false alarm. A second SOS is not
possible until then. Separately, a 60-second dedupe window re-triggers an
existing incident rather than creating a new one.

CONSEQUENCE: a multi-row queue needs multiple assigned residents. Monday's
demo will show one row unless a second resident is assigned.

10.2 THE COORDINATES DIFFER BETWEEN INCIDENTS BY METRES

33.14823 / 33.14826 / 33.14827 / 33.14832. Four incidents were created
during testing and it became easy to lose track of which was which. Read
the id, not the position.

10.3 lastTriggeredAt CAN PRECEDE createdAt

By milliseconds. One is a device clock, the other is the server's. NEVER
compute a duration between them. Age is computed from createdAt against a
serverTime the bridge stamps - the browser clock never enters the
comparison, for the same reason PublicTrackingResponse carries serverTime.

10.4 latitude AND longitude ARRIVE AS STRINGS

Prisma Decimal over JSON. Validate with Number.isFinite before converting;
a non-finite value is OMITTED rather than rendered as NaN.

10.5 Incident.address IS FREQUENTLY NULL AND THAT IS HONEST

See section 6.

11. AUTOMATED POST-INCIDENT REPORTING - ARCHITECTURE DECIDED, NOT BUILT
================================================================================

A requirement recorded this session. NOT to be built until 14A-8 through
14A-11 exist, because those slices produce most of the data it consumes.

It sits AFTER incident closure and BEFORE audit/archival:

  RESOLVED / CANCELLED
    -> freeze incident snapshot
    -> gather timeline, locations, evidence metadata, notifications
    -> generate structured facts (deterministic)
    -> AI summarises a narrative FROM THOSE FACTS ONLY
    -> render report
    -> authorized delivery
    -> audit / archive

  AI IS NOT THE SOURCE OF TRUTH. The database and the timeline are. The
  narrative generator is the highest-risk place in the whole system for the
  omission rule to break, because prose fills gaps invisibly where a null
  field does not. If OPA does not know which guard arrived, the report
  cannot say one did.

FOUR CONSTRAINTS ALREADY KNOWN:

  Some data the pipeline wants DOES NOT EXIST. "Operator actions" and "who
  physically responded" have no source - nothing writes ACKNOWLEDGED and
  dispatch is forbidden by ADR. The report can state notifications sent and
  delivery status, not response.

  DELIVERY HAS NO WORKING CHANNEL. See 9.11.

  "FREEZE THE SNAPSHOT" NEEDS A DECISION. Regenerate on demand from live
  data, or freeze at closure? An insurer reading a report a year later
  should get what was true at closure.

  CANCELLED AND RESOLVED MUST NOT COLLAPSE. See 2.6.

  AND THE GEOCODING LICENCE BEARS ON IT DIRECTLY. A report handed to an
  insurer is neither "End User facing functionality" nor "isolated to the
  specific End User". Section 6.

16. ADDENDUM - 14A-9 INCIDENT TIMELINE, AND WHAT IT FOUND
================================================================================

Written 16 August 2026, after Ultra 36's main body. HEAD a22ef32.

  e9ffac8  API: add safe incident timeline reader projection   14A-9 backend
  a22ef32  Web: add operator incident timeline                 14A-9 website

ELEVEN OF THIRTEEN 14A SLICES ARE DONE.

16.1 WHAT WAS BUILT

The raw timeline endpoint returned findMany with NO select: payload
(arbitrary internal JSON), hash, previousHash, actorUserId, correlationId
and incidentId, straight to any caller. Every other operator-facing
projection in this codebase is explicitly narrow; this one was not a
projection at all.

  GET /incidents/:incidentId/timeline now returns ONLY
    sequence, type, occurredAt, source, display

  display is a PER-EVENT-TYPE ALLOWLIST, because neither extreme was
  right. Measured against a real production incident, one payload held
  reason: 'USER_SAFE' - exactly what an operator needs - alongside
  endedJourneySessionId, an internal UUID.

  THE ALLOWLIST IS A PRESENCE-PRESERVING FILTER, NOT A SCHEMA. A key is
  copied only if the payload has it, tested with hasOwnProperty. close()
  spreads `reason` in conditionally, so a cancellation without one has no
  such key and emitting `reason: undefined` would manufacture a field the
  source never had. Falsy values survive: queued: 0 means nobody was
  reached, and an operator needs that.

  confidenceLevel and confidenceScore are EXCLUDED from INCIDENT_CREATED.
  They come from detection.outcome - the emergency DETECTION model's
  confidence that an activation is genuine, not confidence in the
  location. A deliberate SOS button press scores LOW, and "Confidence:
  Low" beside a live emergency would read as doubt about whether it is
  real.

  actorUserId is EXCLUDED for a reason beyond being a UUID: on the
  production sample it was the RESIDENT on every event, including the
  three the orchestrator wrote. It means "on whose behalf", not "who did
  this". source - MOBILE versus INCIDENT_ORCHESTRATOR - carries the
  distinction that matters.

  THE EXISTING ENDPOINT WAS CHANGED IN PLACE. Measured first: nothing
  consumes it. Not the mobile app, not the website - every website match
  for "timeline" is marketing copy on the hospitals, privacy and home
  pages. A parallel route would have been two contracts free to drift.

  verifyChain STILL USES THE RAW READ. It needs every column to recompute.
  A verify check in the installer fires if that call ever disappears.

16.2 THE WEBSITE HALF

Inline on the detail page, below location and tracking. NOT a separate
route: the timeline is part of the incident, and during an emergency an
operator should not have to leave the page to learn what happened.

  ONE TIMER, NOT TWO. IncidentDetailView already owned the 5-second poll,
  so it also owns fetching the timeline. incident-timeline.tsx is PURELY
  PRESENTATIONAL and fetches nothing. Two timers would allow the header to
  say LIVE while the timeline sat several intervals behind.

  TWO DUMB BRIDGES. /timeline and /timeline/verify, each translating and
  authenticating, neither owning change-detection. A combined endpoint
  taking ?sequence= was designed and rejected: it would put application
  state into the bridge and force response variants for "verification ran"
  versus "it did not".

  LIFECYCLE-AWARE POLLING, and the transition rule is the subtle part:

    SSR fetches detail + timeline + verify, so a deep link to a resolved
    incident arrives complete on first paint.
    The client refetches the timeline only while OPEN or ACKNOWLEDGED,
    PLUS ONE FINAL FETCH ON THE TERMINAL TRANSITION. The event that
    RECORDS a resolution is appended by the same operation that makes the
    status terminal - stopping the moment status flips would miss it, and
    every resolved incident would be missing the record of its own
    closure.
    /verify re-runs only when the last sequence changes. sequence is
    monotonic and unique per incident, so a change IS an append.

  INTEGRITY HAS THREE STATES, NOT TWO: verified, failed, and UNKNOWN. A
  failed request is not a failed chain. Rendering a tampering warning
  because the network was down would be a serious false alarm - and the
  public site already tells customers each entry can be independently
  verified, so the indicator has to mean what it says.

16.4 SOS_RETRIGGERED IS UNREACHABLE FROM THE MOBILE APP

A PRODUCT GAP, NOT A TEST FAILURE, AND THE MORE INTERESTING FINDING.

The backend writes SOS_RETRIGGERED when an SOS arrives for a resident who
already has an open incident. Its payload carries retriggerCount and
secondsSinceInitialTrigger, and public-incident-snapshot.dto.ts notes that
repeated taps may signal RISING DISTRESS - which is why the queue and the
timeline both surface it.

BUT THE ACTIVE-EMERGENCY SCREEN OFFERS NO WAY TO PRESS SOS AGAIN. Its
three actions are:

    I'm safe                        resolves the incident
    False alarm                     cancels it
    Done - keep the emergency active  dismisses the sheet, triggers nothing

So the orchestrator's dedupe-and-retrigger path cannot fire from the
production app. Either the mobile flow is missing a "still in danger"
affordance, or the retrigger path is dead code.

CONSEQUENCE FOR 14A-9: the SOS_RETRIGGERED label and its detail formatter
are written and UNVERIFIED IN RENDER. Do not describe them as working.

CONSEQUENCE FOR THE PRODUCT: worth deciding deliberately. A person whose
situation is deteriorating has no way to say so, and the data model was
built expecting they could.

16.5 THE INTEGRITY-FAILURE BANNER IS UNTESTED

Nothing can break a production hash chain to see it render, and it must
not be faked by hand-editing a live database. Exercise it locally against
opa_test if the rendering matters.

16.7 NEW TRAPS

#203  A BACKTICK INSIDE A DOUBLE-QUOTED POWERSHELL STRING IS AN ESCAPE
      CHARACTER. A JavaScript template literal written that way emits
      WITHOUT its backticks - `${base}/verify` becomes ${base}/verify -
      and the file is written successfully. Every installer verify check
      passed; only the build caught it. Use single-quoted strings with ''
      for inner quotes when emitting JS templates.

#204  .Replace() REPLACES EVERY OCCURRENCE. Two useCallback bodies ended
      with the identical `}, [initialIncident.id]);` line, so adding a
      dependency to one added it to both - including making a callback
      depend on itself. Anchor on something unique to the target.

#205  POWERSHELL 5.1 HAS NO TRAILING-DOT LINE CONTINUATION. A chained
      .Replace() written across lines is a 7.x feature and fails to parse
      before anything runs. Use separate statements.

#206  ANCHORING ON A PROPS TYPE MISSES THE DESTRUCTURING. Adding fields to
      `}: { ... }) {` gave the component props it never bound; tsc
      reported "Cannot find name". The destructuring and the type are one
      anchor.

#207  A CHECK THAT SCANS A WHOLE FILE FAILS ON LEGITIMATE CODE, NOT ONLY
      ON PROSE. `payload:` matched toReaderTimelineEvent's INPUT
      parameter, which is exactly what that function should accept. Scope
      exclusion checks to the block that must not contain the thing -
      here, the exported type - not to the file.
