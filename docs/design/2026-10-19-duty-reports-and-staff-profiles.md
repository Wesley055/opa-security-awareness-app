# OPA Duty Reports and Staff Profiles (design, 19 Oct 2026)

Owner direction, 19 Oct 2026. One shared institutional implementation for every sector: estate, school, bank, organization, oil and gas, aviation, and the rest. No per-industry forks.

## 1. Where Duty Reports sit (no duplication)

Reports / Analytics stays the single reporting destination in the Command Center:

| Section | Answers | Lifecycle |
|---|---|---|
| **Duty Reports** (new) | What happened during an operator's shift | Shift → draft → submitted (or system-generated) → acknowledged by a Facility Admin |
| **OPA Insight** (existing) | What operational data shows over time | Projections and trends |
| **OPA Report / AIR** (existing) | What happened in one incident, and what followed | Immutable versions, corrective actions |
| **Exports** | Authorised PDF/CSV | Only once implemented and verified |

All three read the **same authoritative records**: incidents, timeline events, visitor passes and SafeWalk sessions. A Duty Report **references** those records by id and keeps its own lifecycle. It never copies evidence into a second place where it could drift.

## 2. Critical rules (enforced in code and tests)

1. **Never rewrites incident evidence.** A Duty Report holds references plus the operator's own notes. It has no write path to incidents, the timeline or evidence.
2. **Never counts an incident twice.**
   - An incident appears once per report, in exactly one bucket: *raised this shift* or *carried over, still open*.
   - Facility totals stay in Insight. Duty Reports never add their totals together.
3. **Never claims an acknowledgement that didn't happen.** "Acknowledged" is shown only when a Command Center acknowledgement by an identified operator exists in the timeline, the same rule Insight uses. Everything else reads "Not acknowledged or unknown".
4. **A system-generated report is never shown as operator-submitted.**
   - `origin` is `OPERATOR_SUBMITTED` or `SYSTEM_GENERATED`, and it is immutable.
   - A system-generated report has no notes and no submitter, and is labelled "Generated by OPA. Not submitted by an operator".
5. **Submitted reports are immutable.** A correction is an appended version (`supersedesId`), like the AIR.
6. **Operators never see or type an admin's email.** OPA routes the report to the facility's active Facility Admins.
7. **Snapshot cut-off.** Each report records `sourceCutoff` and a `sourceDigest` of the referenced records, so a later change to an incident is visible as "changed since this report", never silently merged in.

## 3. Workflow

1. **Start shift.** The operator taps **Start duty** in the Command Center. This records an identified staff member and an assigned facility.
2. **During the shift**, OPA collects verified records for the window: incidents and their acknowledgement state, gate and visitor entries, departures and overstays (when EstateFlow is on), and SafeWalk sessions and alerts.
3. **End shift.** The operator taps **End duty and submit report**. OPA shows the prepared summary, and the operator adds observations, handover items and unresolved issues.
4. **Submit.** OPA does three things:
   - sends an in-app notification to the facility's active Facility Admins;
   - sends an optional email to the same admins (looked up by OPA, never shown to the operator);
   - writes an audit event `DUTY_REPORT_SUBMITTED`.
5. **Backup.** If a shift is still open when it reaches its maximum length (default 12 hours), or at the facility's day boundary, OPA closes it and creates a `SYSTEM_GENERATED` report from the records alone.
   - **Safeguard (owner, 19 Oct):** a backup report does **not** discharge the operator's obligation. The shift is marked `endedBy = SYSTEM` and its operator report as **Missing**. The admin sees "Operator report missing; OPA generated a backup summary". The operator is still asked to submit their report, which is linked to the shift as `OPERATOR_SUBMITTED` and late. The backup stays visible beside it, unchanged.
6. **Review.** A Facility Admin opens the report under Reports / Analytics → Duty Reports and taps **Acknowledge**. Acknowledging is audited and doesn't change the report. Unacknowledged reports and open handover items show as exceptions.

## 4. Sector sections (configuration, not code forks)

There is one engine. Each sector profile decides which sections appear and what the people are called. A section appears only when the facility has the module that feeds it, so a report never shows an empty "Visitors" section to a facility without EstateFlow.

| Sector | Members called | Default sections |
|---|---|---|
| Estate / security agency | residents | Incidents, visitor entries and departures, overstays, SafeWalk, handover |
| Bank | customers / staff | Incidents, alarms (SOS), access exceptions, handover |
| School | students / staff | Incidents, visitor appointments, pick-ups and early dismissals (when available), handover |
| Organization (corporate) | staff | Incidents, visitor and contractor access, security observations, handover |
| Oil and gas, aviation | staff | **Roadmap only, not built.** These arrive with the Insight industry modules (Insight Core → Insight Energy → Insight Aviation, backlog "OPA Insight industry modules"). Until then, these sites get the generic sections: incidents, handover and operator observations |

Sections whose source data doesn't exist yet (patrols, attendance, alarms from external systems) are shown as **operator-entered observations** with a category. They are never shown as system-verified counts.

`FacilityType` gains `ESTATE`, `SCHOOL`, `BANK` and `ORGANIZATION` (owner approved). Quartz moves from OTHER to ESTATE.

**Relationship to Insight:** Duty Reports is not built on Insight and doesn't change it. Both read the same incident records with the same acknowledgement rule, so their numbers agree. The sector sections are the operator-shift view of the same industry roadmap: Insight Energy and Insight Aviation (permit-to-work, contractor competency, HSE, occurrence reporting, airside access) stay **planned, not built**, are presented on Wednesday as roadmap only, and OPA never claims certification or regulatory approval.

## 5. Staff profiles (shared institutional workspace)

For Facility Admins, Operators and Technical Support, under one **My profile** page:
- the verified name, read-only (changes go through the admin);
- the profile photo;
- the assigned role and facility, read-only;
- contact preferences (email for duty reports, on/off);
- **password change**, which needs the current password, revokes the other sessions and is audited;
- **active sessions**, with sign out of one session or all others;
- **sign out**.

**Photo rule:** operators must have an approved photo before they can **start a duty shift** (the reporting record). Responders already on duty aren't blocked mid-shift; they're asked to add a photo at their next start of duty.

**Safeguard (owner, 19 Oct): duty state and photos never gate emergency response.** The incident queue, incident detail, map, acknowledgement and every SOS action stay fully available to an authorised operator whether or not they have started duty or have a photo. If an SOS arrives while an operator has no duty shift, they respond as normal, and the incident appears in the next Duty Report as carried over. Tests assert the queue and acknowledgement work for an operator with no photo and no shift. A new operator photo is approved by a Facility Admin before it counts. Photos are stored privately in Azure Blob Storage and served through short-lived signed URLs. They are visible to staff of the same facility and, during an active SOS, to the resident being helped, who sees the responding operator's name and photo (agreed earlier in the backlog).

## 6. Data model (one migration)

- `FacilityType` gains `ESTATE`, `SCHOOL`, `BANK` and `ORGANIZATION`.
- `User` gains `photoKey` (nullable) and `photoUpdatedAt`.
- `DutyShift` has: id, facilityId, operatorId, startedAt, endedAt, endedBy (`OPERATOR` or `SYSTEM`).
- `DutyReport` has: id, shiftId, facilityId, version, origin, submittedBy (null when system-generated), submittedAt, sourceCutoff, sourceDigest, document (JSON of references and counts), notes, handoverItems (JSON), acknowledgedBy, acknowledgedAt and supersedesId. Each shift has a unique version per report.

## 7. Release

These changes are additive only. No existing column changes, so the previous build keeps working against the new schema, and a swap back stays possible. It goes out as a supervised release with the migration, ahead of the Providus presentation. It is web and API only: **no app build is needed.**

## 8. Acceptance (E2E)

- Philips starts duty without a photo → he is asked to add one → he adds one → duty starts.
- An SOS is raised and acknowledged during the shift → it appears once, marked acknowledged.
- A second SOS that is not acknowledged → it is shown as "Not acknowledged or unknown".
- Philips ends duty, adds a note and a handover item, and submits → Matt gets the in-app notification and the email. Philips never sees Matt's email.
- Matt acknowledges → audited, and the report is unchanged.
- A shift left open past 12 hours → a system-generated report, labelled as such, with no submitter.
- A password change on the profile page → other sessions are signed out and the change is audited.
