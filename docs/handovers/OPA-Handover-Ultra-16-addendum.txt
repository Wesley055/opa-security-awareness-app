## A2. CORRECTIONS TO PARTS 1-3

### A2.1 "NO INFRASTRUCTURE-AS-CODE EXISTS ANYWHERE" IS FALSE

Stated in part 2 section 11 and part 1 Tier 3 item 16. **Wrong.**

**`.github/workflows/main_opa-api-production.yml` - 79 lines, READ IN FULL.**

Azure's auto-generated Deployment Center workflow (`main_<app-service>.yml`).
**It triggers on every push to `main`**, so all four commits this session
deployed.

```
on: push to main, plus workflow_dispatch
job build   (ubuntu-latest)
  actions/checkout@v4
  actions/setup-node@v4   node-version: '22.x', cache: npm
  npm ci
  npm run prisma:generate --workspace apps/api
  npm run build --workspace apps/api
  assemble standalone deploy folder:
    mkdir deploy
    cp -r apps/api/dist deploy/dist
    cp -r apps/api/prisma deploy/prisma
    cp apps/api/package.json deploy/package.json
    cd deploy; npm install --include=dev --no-package-lock
    npx prisma generate
    npm prune --omit=dev
  actions/upload-artifact@v4  (include-hidden-files: true)
job deploy  (needs: build)
  azure/login@v2  - OIDC, three repo secrets AZUREAPPSERVICE_{CLIENTID,TENANTID,SUBSCRIPTIONID}_<guid>
  azure/webapps-deploy@v3  app-name: opa-api-production, slot-name: Production
```

**Three gaps, all real:**

1. **NO `prisma migrate deploy` STEP.** The pipeline never applies migrations.
   This is why production drifted five migrations behind - see A3.
   **Adding it is not trivial:** GitHub runners have dynamic IPs and Azure
   Postgres firewalls by IP, so it needs either "Allow public access from any
   Azure service" enabled or a different execution location. **And
   `npm prune --omit=dev` strips the Prisma CLI from the published bundle**, so
   it cannot be run from the App Service afterwards without reinstalling it -
   which is exactly what the parallel session had to do by hand.
2. **NO TEST GATE.** Every push to `main` deploys regardless of `jest`. Adding
   `npx jest` before the build step is a two-line change.
3. **Node 22.x in CI, v26.5.0 locally.** CI does not test what you run. The App
   Service has its own Node setting which was NOT checked and may be a third
   value.

**`found=1` for deployment-ish files across the repo: `docker-compose.yml` only**
(local Postgres and Redis). **There is NO Dockerfile.** This is a code
deployment, not a container - App Service runs `node dist/main.js` via the
`start` script.

**`apps/api/package.json` scripts, measured:**
```
build           nest build
lint            eslint "{src,test}/**/*.ts" --max-warnings=0
start           node dist/main.js
start:dev       nest start --watch
test            jest
test:cov        jest --coverage
test:int        jest --config jest-int.config.ts --runInBand
prisma:generate prisma generate
prisma:migrate  prisma migrate dev

```

### A2.2 THE API IS NOT RUNNING - MEASURED, 503

```
GET https://opa-api-production-g4f6cxdyanfbaub0.southafricanorth-01.azurewebsites.net/api/docs
-> WebException, resp_status=503, dns=4
```

**DNS resolves and Azure's front end answers, so the App Service exists and
there is no healthy container behind it.**

**THE CRITICAL INFERENCE: the deployed build is CURRENT, not stale.** A build
predating `ProviderConfidenceValidator` would boot fine. It does not boot.
**Therefore production is running this repo's code, and that code refuses to
start.** ADR-012 is confirmed as the live cause, not a theory.

**Consequence for sequencing: there is NO running build to fall out of step
with.** Applying migrations to production is safe right now - nothing can query
the new tables until something boots. That removes the usual
migrate-and-deploy-together constraint.

**`/api/docs` is the right probe** - Swagger is published unconditionally, needs
no auth and no database. **Note App Service cold starts take 30+ seconds**, so
allow a long timeout and run twice before concluding.

### A2.3 `OPA_ALLOW_MOCK_PROVIDERS` - THE ABSENCE IS THE ACTIVE CAUSE

Parts 1-3 record it as absent and treat that as confirmation the ban held. True,
but incomplete: **its absence is precisely why nothing boots.**

The reasoning "there are no users yet so it does not matter" is **coherent as a
priority but wrong as a mechanism.** `onModuleInit()` runs when Nest builds the
module graph, before any request is served. It counts registered MOCK providers
and throws. **Zero users, zero traffic, still throws.**

**Do not resolve this by setting the variable** - three documents ban it and
part 2 section 9b.3 explains why. **Resolve it by deciding ADR-012.**

## A6. NEW TRAPS

**#90 - `---` IN A PASTED-BACK CONSOLE BLOCK PARSES AS AN OPERATOR.**
Section separators written as `"--- thing ---"` are harmless when sent as a
command, but when a whole previous output block is pasted back, PowerShell reads
`---` as a decrement and throws `Missing expression after unary operator '-'`.
**Use `"=== thing ==="`.** No operator meaning, same readability.

**#91 - `Measure-Object -Line` COUNTS NON-EMPTY LINES ONLY.**
A 94-line file with a blank line between every content line reports 34. This
briefly looked like evidence of a shorter earlier revision of a file when it was
just the same file measured differently. **For a true line count use
`(Get-Content -LiteralPath $p).Count`.**

**#92 - `curl` IN POWERSHELL IS AN ALIAS FOR `Invoke-WebRequest`.**
`-X`, `-H`, `-d` are not its parameters. **Use `curl.exe`** - which parts 1-3
already do in the website section, but a suggested verification command in the
parallel session did not. Combined with trap #56 (`\"` is not an escape), a
copied curl command will fail confusingly or hang at `>>`.

**#93 - A CATCH BLOCK NEEDS ITS OWN CONTROL.**
`catch { $_.Exception.Response }` printed `status=` empty because the exception
carried no `Response`. **Print `err_type`, `err_msg`, and an explicit
`resp_status=NONE` branch**, so a failure is distinguishable from a silent one.
Same family as the `probe=`/`scanned=` rule, applied to error paths.

**#94 - A SUCCESSFUL DEPLOY IS NOT A RUNNING APP.**
Azure reports deployment success once files are copied. The Node process starts
afterwards and can die immediately, leaving a green pipeline and a 503.
**"Deployed", "running" and "serving requests" are three different claims.**
The parallel session asserted all three from evidence for the first.

### A7.1 `docs/future/ussd-fallback.md` IS CONVERSION-DAMAGED

94 lines, **BOM + CRLF**, `bytes=1870` vs `chars=1846`. Escaped markdown
(`\#`, `\*\*`, `1\.`), `&#x20;` entities, and a blank line between every content
line - a Word-to-Markdown round trip. **It renders wrong on GitHub.**

**Its `## Fallback decision tree` heading at line 21 is followed immediately by
the next heading. The decision tree itself is MISSING.** Trap #39 made concrete.

**It was born damaged:** `git log --follow` shows exactly one commit,
`c427571`, and the blob is 94 lines - identical to the working copy. **Git
cannot recover it.** `OPA-Master-Roadmap.md` in DocStaging only contains a
pointer to the file. **The source `.docx` was not located.**

**Content that survives and is worth keeping:** USSD needs cellular signal, a
supported network, **a registered short code via a telecom or aggregator
requiring formal approval**, and a session capped around 2-3 minutes. **Never
transmit evidence, medical records or long location payloads over USSD.** A
USSD-triggered incident should confirm **location/community** - i.e. a
pre-registered location, the same shape a fixed duress button needs - create a
bare incident, send a short confirmation.

**Its roadmap places USSD LAST**, after a validated product and a real telecom
partnership. **That contradicts market commentary treating USSD as an open entry
point: it is gated on a partnership OPA does not control**, structurally the
same as 10C's procurement gate. Its own roadmap is also stale - it lists the
React Native app as "next" when it is built and device-verified.

### A7.3 COMMAND CENTRE - SCOPING DISCUSSED, NOT DECIDED

**It is a WEB dashboard, not a mobile app.** Institutional staff at a desk. The
public tracking page is the precedent: web-only, no download, no login, reached
by a tokenized SMS link.

**Four surfaces exist conceptually; three are built:** mobile app (individual,
the only trigger), tracking page (contact, token link), marketing website, and
the Command Centre (institution staff) which **does not exist at all** - the
website has exactly one interactive component.

**KEEP THE ADR-013 BOUNDARY: viewer, never console.** Incident list, live
position, report retrieval, **acknowledgement display** - yes. Responder
assignment, status tracking, escalation - no.

**THE QUESTION THAT CHANGES THE DESIGN AND IS UNANSWERED: is the institution
buying for its STAFF or for its CLIENTS?** Staff enrolment can be mandatory and
bulk-loaded from an HR list, with a known headcount and a buyer who controls
adoption. Client enrolment must be voluntary, self-service and consent-based - a
different data model and a different NDPA position. **Decide before building.**

**What exists to build on:** the `Facility` model and access guards are real and
tested. **What does not:** any authenticated web area, a facility-scoped
incident list endpoint, any enrolment or invite flow, and medical fields (Sprint
12, confirmed absent from the database).

**Zero-download triggering is NOT possible today** - `sos.tsx` is the only
trigger. Zero-download applies to *viewing*. For hospitals the real
zero-download trigger is **hardware** - a wall button or badge - which fits
`TODO.md:1322-1333`'s sensor principle, and whose **fixed known location solves
the required `latitude`/`longitude` trivially and sidesteps indoor positioning
entirely.** It needs a device or third-party auth model, which does not exist.

### A7.4 OUTREACH - A DRAFT WAS REVIEWED AND SHOULD NOT BE SENT AS WRITTEN

A drafted estate email claimed: an active pilot; an emergency command centre
platform; zero app downloads to trigger; a security team dashboard that maps
responders and shares data with emergency services; and **full NDPA
compliance**. **Every one of those is false today**, and the dashboard claim is
precisely the coordination drift ADR-013 warns against.

**What is true and worth leading with:** tokenized SMS links opening a live map
in any browser with no download or login; a device-verified ten-second cadence;
and a tamper-evident record - location fixes and timeline events both chained,
with a verifier.

**Recommended framing: pre-pilot, seeking one or two design partners.**
Stronger than a fake pilot, and it matches the differentiation document's own
argument that an institutional buyer finds the limit anyway and trusts whoever
named it first.

**Two things to fix before any demo:** render the tracking page (never done, 54
real fixes waiting), and the `contactsNotified` "0 contacts" bug.
