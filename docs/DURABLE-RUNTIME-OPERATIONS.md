# Production runtime custody and controlled rollout

This is the candidate's authoritative lifecycle procedure, superseding manual 24-hour API renewal only after separately authorized rollout. Existing historical receipts and runbooks are preserved. Status: not production accepted. No production mutation or signing is authorized by this document.

Reconcile the current `opa-api-production` resource, resource group `opa-production`, exact active policy digest supplied for this incident, actual configuration and schema-35 checksums using read-only operations. Verify actual App Service/SCM access and immutable ZIP mounting; Unix mode 0600 alone is not separation when SCM and API share the owner. Block deployment if these properties cannot be established. Do not add infrastructure implicitly.

Keep `/home/opa-runtime-custody/artifact.manifest.json` and the downloaded cache `/home/opa-runtime-custody/state.signed.json` outside wwwroot. The authoritative state is the latest secret version `opa-api-runtime-custody` in the exact signed Key Vault origin. Startup and supervision always fetch it using App Service managed identity; there is no local-only fallback. Explicitly authorize object creation/update and any identity role assignment before production mutation. Require get-only runtime identity access and separately controlled custodian writes. Verify the runtime identity cannot set/delete/recover custody secrets, assign roles or change access policies. Application storage keys grant no Key Vault write permission. No additional infrastructure has been created.

The API policy path points to a signed runtime-api authorization outside wwwroot. Store signed state versions and their hashes in the existing audited operations custody, never overwrite historical evidence. Before every privileged custody restoration compare the latest externally audited custody sequence and revocations. Restore of a once-valid older authoritative state is not permitted. Managed identity or Key Vault unavailability intentionally fails closed; monitor both dependencies.

## Bounded production gate

Explicit authorization must name: installing the reviewed corrected ZIP on opa-api-production; installing the exact signed runtime authorization, manifest and custody state; changing only OPA_BUILD_SHA and OPA_ENVIRONMENT_POLICY_FILE as required; configuring immutable mounting if needed; and one controlled restart. The approval must include exact hashes, latest custody sequence, a maintenance window, accountable operator, abort thresholds and rollback artifact. No SQL, migrations, signing-key changes or trusted-registry changes are part of this approval.

Immediately before execution, recheck healthy production, exact baseline build/policy/settings fingerprint, live 35-migration history, current custody and no unapproved deployment. Transfer files to a new evidence-tagged staging location, hash-check them, verify signatures and configuration, then atomically publish approved custody and policy. Deploy only the reviewed ZIP with the short-lived deployment approval still valid. Keep all unrelated settings byte-for-byte. Stop on drift.

After the authorized restart, require both health endpoints HTTP 200, exact new build, schema-35 readiness and successful signed runtime admission on every observed instance. Verify worker initialization without real SOS dispatch. Record live acceptance separately from rehearsal. Demonstrate a separately authorized restart after the former deployment deadline passes; recurring deployment-policy renewal is not required. Remain pending until this evidence exists.

## Rollback and recovery

Never redeploy the original expiration-coupled ZIP or repoint to a version-1 API policy. The fallback must already contain this durable verifier, immutable manifest enforcement and custody supervision, have its own exact signed runtime authorization, and be explicitly active in the latest custody state. If no such fallback exists, stop the rollout before deployment. Restoring a revoked authorization or older custody snapshot is prohibited. Restore configuration only when it matches the fallback's signed bindings. Recheck schema-35 checksums, health and build after an explicitly authorized recovery restart. Do not execute the seven migrations.

## Revocation and rotation

For runtime revocation, obtain explicit emergency authorization, record reason/incident/operator and exact authorization or SPKI fingerprint, issue a new signed custody state at the next sequence, remove affected active authorizations and append revocations. Independently verify, serialize custodian updates, recheck the latest current secret version/sequence, and create the next Key Vault secret version, and retain both old and new receipts. All instances must reject new startup immediately and existing processes terminate at their next custody check (up to 60 seconds plus bounded identity/Key Vault request timeouts and scheduling). Verify instance termination and worker inactivity. Do not remove revocation entries to recover service; approve a replacement authorization.

For emergency key rotation, separately authorize trusted-registry/key changes. Stage the new public authority in an exact reviewed verifier artifact and sign replacement runtime authorization/custody under an approved trusted authority. Preserve a compatible durable fallback, then perform the separately authorized rollout. Revoke the compromised fingerprint in custody and confirm all instances enforce it. A cached registry does not learn new keys without restart; plan the ordering explicitly. No key or registry has been changed in this task.

## Monitoring and availability

Monitor health/readiness, build and instance identity, successful admission, custody sequence/digest, revocation enforcement and custody-check failures. Alert immediately on custody missing/tampered, artifact drift, unauthorized configuration, restart failure or unknown instance. Alert ahead of expiry only for deployment, migration, signing and other privileged approvals. Runtime authorization has no recurring renewal timer. Assign a tested alert destination, acknowledgement and escalation owner before acceptance. Audit every runtime admission and custody change using existing operations/telemetry facilities; do not log secret values. Do not claim production acceptance from local tests.

Key Vault custody uses the existing production vault; its signed origin is verified before any token or secret request. Keep the custody envelope below 25,000 bytes, retaining all still-relevant revocations and archiving historical versions externally. No version-pinned read or offline fallback is allowed.
