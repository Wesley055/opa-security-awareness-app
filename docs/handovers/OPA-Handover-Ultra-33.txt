3.4 WHAT WAS BUILT

A TaskManager background task that CAPTURES ONLY. It opens its own store
handle, reads the persisted capture sequence, writes one row, stops. No
flush, no replay, no fault handling.

That boundary is not laziness. A TaskManager task runs in a SEPARATE JS
CONTEXT: none of journey-tracker.ts's module state exists there - not
queueStore, not sessionId, not captureSeq, not replayFault, not flushing.
Replay policy depends on all of them, so replay stays in the foreground and
the tracker drains what accumulated when the app returns.

THREE DESIGN POINTS, each of which was WRONG in the first draft and corrected
on review. They are recorded because the wrong version looked reasonable:

  EXCLUSIVE-OR CAPTURE, NOT ADDITIVE. The first draft ran
  startLocationUpdatesAsync alongside watchPositionAsync and claimed INSERT
  OR IGNORE would deduplicate. IT WOULD NOT. The idempotency key is
  sessionId:timestamp:sequence - two independent subscriptions produce
  different timestamps and draw different sequences, so BOTH ROWS INSERT.
  That is doubled history in an emergency record. Now: background granted ->
  the task owns capture; denied or unavailable -> the foreground watcher.
  Never both.

  source: 'background', NOT 'foreground'. The first draft wrote 'foreground'
  from a background context and argued a migration would be needed. MEASURED
  AND FALSE: TRACKED_SOURCES in ingest-fixes.dto.ts is already
  ['foreground','background','manual'], the column is String @db.VarChar(32)
  not an enum, and tracking-state.ts already derives an origin from
  'background'. NO API CHANGE, NO MIGRATION. Writing false provenance into a
  tamper-evident record to avoid a five-minute check is indefensible.
  journey-queue-store.ts's hydration guard needed the value too - without it
  the queue would ACCEPT a background fix and then refuse to read its own row
  back on replay.

  ACTIVE_INCIDENT_QUEUE_DEPTH = 7200, replacing MAX_QUEUED_FIXES = 600 and
  MAX_FAULTED_QUEUED_FIXES = 6 * MAX_BATCH. Ultra 27 section 4.6 measured 4-5
  fixes per 15s cycle on a MOVING device with DISTANCE_INTERVAL_M = 0, so 600
  is about twenty minutes before the OLDEST fixes are evicted - and the start
  of a journey is exactly what an investigation needs. 7200 is roughly four
  hours. The faulted ceiling uses the same number rather than a lower one: if
  upload is failing during a transport event, that is precisely when MORE
  history should be preserved.

THE FOREGROUND SERVICE. Since Android 10, background location WITHOUT a
persistent notification is throttled to a few updates per hour - which is
what a 3617-second gap looks like. The notification is the price of not being
throttled, and a person being tracked during an emergency has a right to see
it happening.

SESSION ID ACROSS CONTEXTS: SecureStore, key opa-background-session-id.
journey_queue_meta.value is INTEGER NOT NULL and a session id is a UUID, so
the meta table would have meant migrating the 10B schema. api.ts already
reads tokens from SecureStore per request, so the pattern was established.

PERMISSION DENIAL IS NOT FATAL. Background permission is requested only AFTER
foreground is granted, the order Android requires. A refusal returns false
and the foreground watcher starts instead. The SOS is never blocked.

3.5 THE COLD-START BUG - IDENTIFIED, NOT FIXED, AND THE PRIME SUSPECT

_layout.tsx fires stopTracking() whenever isAuthenticated is false, as a
defensive reset. Its comment says "stopTracking is idempotent, so the
false-on-cold-start pass is harmless". IT WAS. It stopped being harmless the
moment stopTracking() started calling stopBackgroundCapture(), which deletes
the SecureStore session key and unregisters the OS task.

MEASURED IN THE TREE AT 83ffcfa - the guard is NOT there:

    useEffect(() => {
      if (!isAuthenticated) {
        void stopTracking();
      }
    }, [isAuthenticated]);

The isLoading guard was discussed, drafted and NEVER COMMITTED. sos.tsx's
`void stopTracking()` change DID land in the same commit, so part of that
work is in and part is not - which is exactly how this kind of gap survives.

The failure mode: on every cold start, before auth resolves, isAuthenticated
is false, the session key is wiped and the task unregistered. Every
subsequent background fix would log "no active session - discarding
background fix". SILENT, and indistinguishable from the defect being fixed.

Fix: guard on !isLoading and add isLoading to the dependency array so the
effect re-runs when auth resolves and a genuine logout still tears down.

DIAGNOSE BEFORE APPLYING. It is a strong candidate for the zero-fix result,
but it is not the only one, and stacking a second speculative change on an
undiagnosed failure is how the first one got missed.

THERE IS NO TEST FOR THIS EFFECT. If _layout gains a spec, the scenario is
two lines and worth having.

TWO THINGS THAT MAKE THIS HARDER TO REASON ABOUT THAN THE 10 AUGUST FAILURE:

  wants belt and braces even at the cost of some duplicate rows.

  'activation' is a FOURTH source value nobody had mentioned. It is written

  by_source output.

10. TRAPS ADDED THIS SESSION
================================================================================

Numbering continues from Ultra 32.

#155  A DOCUMENTED RECOMMENDATION IS NOT A MEASUREMENT. Ultra 28 section
      4.1b's "remove REDIS_URL" was measured against the runtime path, where
      Redis genuinely is optional, and never against the STARTUP path. It
      was carried through four handovers and it took production down.

#156  CONFIG VALIDATION IS PART OF THE BOOT PATH AND NEEDS ITS OWN TESTS.
      Every existing spec assumed a validated environment, so none of them
      could see a defect in the validator. A schema stricter than the policy
      it enforces passes every test and fails on the first config change.

#157  A CHECK THAT CANNOT DISTINGUISH THE STATES IT EXISTS TO DISTINGUISH IS
      DECORATION. "apiBaseUrl=" printed identically for null and for {}.
      Later, an expo config check printed empty because ConvertFrom-Json ran
      against a stream carrying stderr - and it was reported as a gate.
      Assert on TYPE, and assert the assertion can fail.

#158  A TARGETED TEST RUN IS NOT THE SUITE. journey-background-task.spec.ts
      passed 9/9 in isolation because it mocks TaskManager itself. The full
      suite then failed: journey-tracker.spec.ts had no such mock and the
      tracker now imports the background task. RUN THE WHOLE SUITE.

#159  IDEMPOTENCE COMMENTS AGE BADLY. "_layout fires stopTracking on cold
      start, and stopTracking is idempotent, so it is harmless" was TRUE
      when written and became false the moment stopTracking grew a
      SecureStore delete and an OS-task unregister. When a function gains a
      side effect, grep its callers for comments asserting it has none.

#160  TWO SUBSCRIPTIONS TO ONE QUEUE DOUBLE THE DATA. INSERT OR IGNORE only
      helps when the key is derived from the OBSERVATION. A key carrying a
      platform timestamp and an independently drawn sequence differs between
      two readings of the same position, so both rows insert.

#161  CHECK THE WIRE CONTRACT BEFORE ASSUMING A MIGRATION. 'background' was
      already in TRACKED_SOURCES and the column was VarChar(32). The first
      draft wrote FALSE PROVENANCE into a tamper-evident record to avoid a
      five-minute grep.

#162  A NEW ENUM VALUE NEEDS THE READ PATH TOO. journey-queue-store.ts would
      have ACCEPTED a background fix and then thrown on replay, because its
      hydration guard listed only the old two values.

#163  EAS INIT REWRITES null AS {} IN app.json EXTRA. Expo's serialiser
      represents null that way generally. Any consumer must check the TYPE,
      never the truthiness.

#164  npm install SILENTLY OVERRIDES PEER CONFLICTS; npm ci REFUSES. A cloud
      build running npm ci fails on a conflict that never appeared locally.
      Run npm ci locally before paying for a build.

#165  A FILE CREATED BETWEEN TWO GATE RUNS IS UNCHECKED. app.config.ts
      shipped with a TypeScript error because tsc last ran before it
      existed.

#166  MEASURE LINE ENDINGS PER FILE, EVERY TIME. In one session app.json was
      CRLF while the services were LF; three notification providers were
      CRLF while three others were LF; app.json had been LF two handovers
      earlier. A per-file detector earned its place repeatedly.

#167  THE GAPS BETWEEN LOG LINES CARRY THE INFORMATION. The 26 km defect was
      invisible in the lines themselves - every request was a 201. It was
      the SILENCE between them that mattered. Read timestamps, not just
      messages.
