## 2. WHAT SHIPPED
================================================================================

### 2.1 THE STORE'S MUTATION CONTRACT - 184892e [M]

`enqueue` no longer returns a boolean. It takes an options object and returns
a result:

  interface EnqueueJourneyFixOptions {
    maxQueuedFixes: number;
    deferOverflowEviction: boolean;
  }

  interface JourneyQueueMutationResult {
    inserted: boolean;
    dropped: number;
    durableDepth: number;
  }

  async enqueue(input, options): Promise<JourneyQueueMutationResult>
  async trimToDepth(maxQueuedFixes): Promise<JourneyQueueTrimResult>

[D] THE BOUND AND THE DEFERRAL ARE SEPARATE FIELDS, AND THIS WAS ARGUED. A
nullable bound (`maxQueuedFixes: number | null`, null meaning deferred) was
proposed and REJECTED by the operator, correctly: null would have to mean both
"no bound exists" and "the bound exists but is not enforced right now", and
only the second is ever true. The bound remains defined while enforcement is
deferred. Recorded in ADR-014 s11 so the reasoning survives the code.

[M] `inserted` still means what it meant: `result.changes === 1` from the
`INSERT OR IGNORE`, read from that statement's own result before the metadata
write. The store spec's existing test at `reads insert changes before the
metadata statement` pins that ordering and STILL PASSES - but note it now
guards a THREE-statement transaction while only pinning the first two. See
7.3.

[M] EVICTION AND TRIM SHARE ONE SQL CONSTANT. `EVICT_OLDEST_SQL` deletes by
`queue_id IN (SELECT ... ORDER BY queue_id ASC LIMIT ?)`. Both call sites use
it, so `ORDER BY queue_id ASC` appears exactly twice in the store: once there,
once in `listOldest`.

### 2.2 THE TRACKER IS NOW DURABLE - bc455fc [M]

`enqueue()` is a synchronous wrapper that calls `enqueueDurable()` and
attaches an explicit catch. `flush()` reads `listOldest(MAX_BATCH)`, projects,
posts, deletes acknowledged keys, compares counts, and trims in a `finally`.

[D] THE CAPTURE CALLBACK USES AN EXPLICIT REJECTION HANDLER, NOT A FLOATING
PROMISE. `watchPositionAsync` does not await the promise a callback returns,
so the durable write cannot be awaited. Three options were weighed: floating
promise, staging array with a drain loop, and an explicit catch. The catch
won. A staging array would reintroduce a second in-memory buffer that dies
with the process - the exact loss 9c removes - and SQLite's exclusive
transaction already provides the serialization the staging array was buying.
An unhandled rejection would lose a fix with no local signal, which is
indistinguishable from a fix never captured. Recorded at 56da26a.

[D] CAPTURE SEQUENCE GAPS ARE CORRECT. `captureSeq` increments synchronously
before the async write, so the key is minted first and stays stable across
retries. A failed write burns a number that never reaches a row. The
requirement is monotonic uniqueness, not contiguity. NEVER decrement or reuse
a burned sequence: reuse mints a duplicate key, and Ultra 25 section 6.2
established that key identity is load-bearing for LOCAL DELETION as well as
server dedupe. Recorded at 56da26a.

[M] THE IN-MEMORY ARRAY IS VERIFIABLY GONE. The installer failed closed on any
of: `queue.length`, `queue.push(`, `queue.slice(`, `queue.filter(`,
`let queue:`. All five measured 0 before the write.

### 2.3 THE PROJECTION, AND WHY IT NEEDED ITS OWN TEST [M]

`toPayload(row: StoredJourneyFix): TrackedFix` exists because
`StoredJourneyFix EXTENDS TrackedFix`. That inheritance means the compiler
will let `listOldest()`'s output go straight to `api.post` WITHOUT COMPLAINT -
excess property checks fire only on object literals, never on variables. With
`forbidNonWhitelisted: true`, `queueId` and `sessionId` would 400 the entire
batch of up to 200 fixes ON THE EMERGENCY PATH, with `tsc` exiting 0 and every
call-count assertion passing.

[R] THE TEST THAT GUARDS THIS ASSERTS THE EXACT KEY SET ON THE WIRE:
`expect(Object.keys(sent[0]).sort()).toEqual([...])` against the seven
TrackedFix keys. A test that only checks `toHaveBeenCalledWith` on the URL, or
counts calls, WOULD NOT CATCH IT. If that test is ever weakened, this failure
returns and returns silently.

[M] accuracy and speed are omitted, not nulled, in both directions. `mapRow`
produces an ABSENT key for a NULL column and `toPayload` preserves that with
`!== undefined`. "Column is NULL" and "key absent from JSON" are different
things to a whitelisting validator.

| Condition                          | Response                             |
|------------------------------------|--------------------------------------|
| session missing OR wrong owner     | 404 NotFoundException                |
| session status === ENDED           | 409 ConflictException                |
| recordedAt precedes session        | 400 BadRequestException              |
| recordedAt too far in future       | 400 BadRequestException              |

[M] 409 IS UNAMBIGUOUS ON THIS PATH. Nothing else in the ingest flow throws
ConflictException. A 409 on a fix batch means ENDED and nothing else, so the
client can branch on status alone without parsing a message string. ADR-014
s11's ended-session rule IS implementable as written.

[M] 404 IS DELIBERATELY AMBIGUOUS AND MUST STAY THAT WAY.
`session === null || session.userId !== userId` throws the SAME exception with
the SAME message. This refuses to confirm a session's existence to a
non-owner, which is correct. THE CONSEQUENCE FOR THE CLIENT: a 404 can NEVER
be read as "this row is dead, drop it." It may be a transient identity or auth
problem. Keep the rows.

[M] CLASSIFICATION IS BATCH-LEVEL, AND THAT IS SUFFICIENT. The ENDED check
runs once per request against `dto.sessionId`, before any per-item validation.
Combined with the fact that the payload carries no session id, a batch is
single-session by construction, so there is nothing a per-item classification
would add for THIS rule. ADR-014 s11 says per-item classification is not
exposed; that remains true and now does not matter for the ended-session case.

[M] THE COMMENT AT LINES 251-256 IS A WARNING WORTH CARRYING FORWARD. The
ENDED verdict is read inside the transaction specifically because
`insertFixes` DOES NOT ITSELF REJECT ENDED - it uses status only for the
STARTED -> ACTIVE promotion. The 409 guard is the SOLE protection against
appending to an ended session, and it lives OUTSIDE `insertFixes`. Any future
path reaching `insertFixes` by another route bypasses it silently.

[M] PHASE B REMAINS INVISIBLE TO CLIENTS. Lines 286-289: if any item is

## 4. THE DEFECT bc455fc INTRODUCED - HTTP 400 HEAD-OF-LINE BLOCKING
================================================================================

[M] THIS IS THE NEXT DECISION AND IT IS NAMED HERE SO IT CANNOT BE
REDISCOVERED AS A SURPRISE AT ITEM 10.

The mechanism, in three measured facts:
  1. The server rejects the WHOLE batch on any bad item and writes no
     survivors (section 3, lines 286-289).
  2. The client keeps every row on any non-2xx - correct, and required by
     trap 74.
  3. The queue NO LONGER DIES WITH THE PROCESS.

Together: ONE ROW WITH A TEMPORAL FAULT BLOCKS EVERY ROW BEHIND IT,
PERMANENTLY. It is retried every cycle and fails identically every cycle.
Before bc455fc, process death cleared this. Nothing clears it now.

[M] BOTH 400 CONDITIONS ARE REACHABLE IN PRACTICE, NOT HYPOTHETICAL. A row
persisted across a restart is BY DEFINITION old, which is the `recordedAt
precedes the session` case. Device clock skew produces the future-skew case.
These are exactly the rows 9c exists to protect.

[D] TWO CANDIDATE POLICIES, NEITHER COSMETIC, BOTH WITH REAL COSTS:

  POISON-ROW EVICTION. On 400, drop the oldest row (or the row named in the
  message), log at high severity, continue next cycle. The queue drains. THE
  COST: it deletes captured emergency data on a CLIENT-SIDE INFERENCE about
  which row is bad, and the server's message is the only evidence.

  HALT AND SURFACE. On 400, stop and raise a distinct persistent fault. Loses
  nothing. THE COST: the queue is stuck until Phase C, and a stuck emergency
  queue is its own failure.

[R] DECIDE IT IN ADR-014 BEFORE WRITING ITEM 6. This is the pattern that has
held seven times and this is the decision most likely to be made silently by
whoever writes the retry code first. It is also a PRODUCT question - whether a
fix that the server will never accept is worth holding forever - and it should
not be settled by an implementation detail.

### TRAP #122 - PowerShell -Path DOES NOT EXPAND `**`, AND FAILS SILENTLY [M]

  Select-String -Path apps\api\src\**\*.ts -Pattern '...'

returned NOTHING and did not error. `**` is treated as a single `*`, so only
one directory level below `src\` was searched. The correct form is:

  Get-ChildItem apps\api\src -Recurse -Filter *.ts | Select-String -Pattern '...'

[R] THIS IS THE THIRD PATH-RESOLUTION TRAP IN THE FAMILY (#120, #121) AND THE
ONLY ONE THAT FAILS SILENTLY. An empty result reads exactly like "no matches
exist." It cost one full round of reasoning about a file that was there all
along.

### TRAP #123 - [bool] ON `git diff --quiet` IS ALWAYS FALSE [M]

  "changed=" + [bool](git diff --quiet -- path/to/file)

prints `changed=False` whether or not the file changed. `--quiet` writes
nothing to stdout and signals through the EXIT CODE, so the pipeline receives
`$null` and `[bool]$null` is `False`. The correct form:

  git diff --quiet -- path/to/file
  "changed=" + ($LASTEXITCODE -ne 0)

[R] SAME FAMILY AS TRAP #119: git communicating through a channel the
pipeline discards. Prefer `git status --porcelain` for whole-tree state; it
is harder to misread.
