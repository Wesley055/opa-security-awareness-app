# Staging migration diagnostics

The wrapper retains structured stages, exit code/signal/duration, parsed Prisma and SQLSTATE codes, and fixed error classifications. No raw process output is persisted. Sanitization removes known secrets and their encoded/hash forms, URIs, query values, connection fields and Bearer tokens before classification. The artifact projector accepts only fixed stage/class names and typed process metadata.

The caller preserves the wrapper artifact and exit status inside its sanitized audit even when migration fails. The wrapper still invokes the same single prisma migrate deploy command between the same environment checks. Prisma validation remains in the caller and is marked delegated/skipped in wrapper diagnostics. The optional TypeScript observer does not change checks or SQL. Cleanup failures remain visible and do not erase the primary wrapper failure. Raw errors and runtime credentials never belong in GitHub output or artifacts.

Review mode runs permission diagnostics in BEGIN READ ONLY with ROLLBACK in finally. It verifies the fixed staging role/database, reads database/schema privileges, PL/pgSQL and UUID prerequisites, installed extensions, TLS and timeout settings. A nonblocking transaction advisory lock on Prisma key 72707369 is released by rollback. It creates no migration objects. Prisma engine connectivity uses the existing sentinel/history preflight. The review trigger must remain execute:false; it never invokes the migration wrapper or disposable-database custodian.

All 35 migrations are unchanged. Prerequisites include public schema USAGE/CREATE, ownership of objects created by the migration role, PL/pgSQL USAGE, built-in gen_random_uuid(), and adequate DDL lock timeouts. No CREATE EXTENSION or concurrent index statement is present. Delivery and SafeWalk delivery migrations contain explicit transactions; do not add blanket transaction wrapping. Enum additions/replacement depend on directory order. UserRole replacement rejects legacy HOSPITAL_STAFF data, which is absent in the empty staging baseline. Partial/unique indexes can fail on conflicting data; the clean staging baseline avoids existing-row conflicts. Evidence/Insight from its isolated branch is not part of these 35 migrations.

The earlier failure remains unattributed because the old wrapper discarded its diagnostics. A successful read-only check does not prove future DDL execution. Any clean retry requires separate authorization and fresh SHA/policy/lease bindings; no historical migration edits, reset, db push or manual history changes are justified by missing diagnostics alone.
