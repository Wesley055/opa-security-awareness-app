### 9b.2 HOW THE CONCURRENCY TEST WAS MADE HONEST - trap #11

**`advisory-lock.int-spec.ts` names the hazard in its own header: a badly
written concurrency test passes whether or not the lock exists.** Its defence is
a CONTROL CASE, and the new spec copies that shape exactly.

**Test 1 - contended.** Client A opens a transaction, takes
`pg_advisory_xact_lock(3, hashtext(incidentId))`, sets a flag, and holds on an
unresolved promise. `waitFor` confirms A holds. Client B then calls
`recordEvent` for the SAME incident. After a 400ms sleep:
```
expect(bFinishedAt).toBeNull();
```
**That is the assertion that fails if the lock is absent, uses a different
classid, or is keyed on anything other than `incidentId`.** It pins the KEY, not
merely that some lock is taken.

**Test 2 - the control.** Same classid held, DIFFERENT incident. B must complete
immediately. **Without this, test 1 could be measuring connection
serialisation rather than the lock.**

**Test 3 - the outcome.** Two `recordEvent` calls started before either is
awaited, via two clients. Assert sequences `[1, 2]`, genesis `previousHash` null,
second linking to first, and `verifyChain` valid. **Without the lock both
writers read a null tail, both compute sequence 1, and the second insert violates
`@@unique([incidentId, sequence])` with P2002.**

**Two enabling facts already existed in the harness and were not recorded in
Ultra 15:**
- **`makeTestClient()`** in `prisma-test-client.ts:17`, explicitly for
  "tests that need genuinely concurrent connections."
- **`truncateAll()` enumerates from `pg_tables`**, so `Incident` and
  `IncidentTimelineEvent` were already covered with no harness change.
  **Verified rather than assumed** - a hardcoded list would have leaked events
  between tests and produced a green run today with a mystery failure later.

**Result: 6 suites / 24 tests, ~12.1s. The concurrency spec alone takes 5.258s**,
consistent with two 400ms holds plus real transaction work - i.e. the contention

### 9b.5 EVIDENCE ARCHITECTURE - ADR-013 OWED, CONTENT DECIDED

**Write these up; the reasoning is what will otherwise be lost.**

**1. Priority ordering, and evidence must never delay location.**
```
location -> SOS/status messages -> telemetry -> audio -> photos -> video
```
A 200-fix batch is a few KB; thirty seconds of video is several MB. **On a weak
connection during an emergency, video uploads would starve the location updates
- degrading a proven capability to add an unproven one.**

**Implementation note:** location and evidence go to **different endpoints** -
`POST /journey/fixes` versus a multipart blob upload with a **50MB in-memory
buffer cap**. So the priority queue is client-side scheduling across two very
different transports, not one queue.

**2. AUDIO ABOVE PHOTOS.** A phone in a purse, pocket, face-down or in a car
console produces twenty unusable photos, but a microphone in the same purse
still captures speech. **Audio does not depend on where the camera points.**

**3. THE BINDING CONSTRAINT ON AUDIO IS BYSTANDER CONSENT, NOT USER CONSENT.**
The user can consent to being recorded. **The user CANNOT consent on behalf of
the shopkeeper, passer-by or colleague whose voice ends up in the file.**
Location records where *you* were; audio records what *other people said*.

**Correct framing: silent to the user's attacker, documented in the legal basis.**
**A question for counsel about a specific jurisdiction, not a design toggle** -
and the one item that genuinely blocks on NDPA.

**Also: an audio recording is only evidence if it is admissible.** A file
captured without a defensible consent basis may be worse than nothing, because it
invites a challenge to the whole record - **including the location half that
currently IS clean.**

**4. TWO INTEGRITY MECHANISMS, KEPT SEPARATE.** Location fixes have a **hash
chain**, which proves nothing was REMOVED. Evidence has **per-object sha256**,
which proves an individual file was not altered. **A chain is strictly stronger.**
`GPS_LOG` exists as an `EvidenceType` and **folding location into per-object
evidence would WEAKEN it.** Right model: two mechanisms, one timeline referencing
both. **NOW THREE MECHANISMS AND ONE TIMELINE: the timeline itself is chained
too, which strengthens this design rather than complicating it.**

**5. AI SUMMARIES ARE NOT EVIDENCE OBJECTS.** A captured artifact and a derived
interpretation cannot carry the same evidentiary status. **The first competent
challenge attacks the summary and discredits everything adjacent to it.** Derived
material belongs in a **separate, clearly-labelled layer that REFERENCES
evidence.**

**6. DEVELOPMENT AND DEPLOYMENT ARE SEPARABLE.** The pipeline, APIs, storage,
upload queues and timeline model can be built while capture release waits on
regulatory work. **And most of that pipeline already exists.**

**7. RESPONSE COORDINATION - DEFERRED, NOT REJECTED.**

**OPA is the evidentiary layer for now.** Coordination is a real future product.

**Why deferred rather than rejected.** Independence is the only structurally
uncopyable advantage today - **a responder cannot produce neutral evidence about
their own response.**

**Critically: the hash chain does NOT rescue this.** Cryptographic integrity
proves the record was not altered after the fact. It says nothing about whether
the party who wrote it had an interest in what it said. **Tamper-evidence is not
independence.**

**The boundary while deferred: VIEWER, NEVER CONSOLE.** Incident list, live
position, report retrieval - yes. Responder assignment, status tracking,
escalation management - no. **Stated explicitly because a viewer drifts into a
console one reasonable request at a time.**

**Where the line falls:** notifying contacts is *alerting*. Giving a responder
scoped live location is *providing information*. Recording that a responder
acknowledged at 14:02:40 is *observing someone else's action* - which is why
acknowledgement is so valuable: **it proves response time without OPA
participating in the response.** Coordination starts at *deciding and directing*.

**What would justify revisiting:** a failed or declined partnership with a
response operator; institutional buyers requiring dispatch as a condition of
purchase; a funded route to actual response capability; or OPA's record becoming
commodity rather than differentiator.

**The honest counter-argument, recorded:** coordination is where recurring
revenue and stickiness usually live. **This is a bet, not a theorem.**

**8. PARTNER APIs COME AFTER PRODUCT-MARKET FIT**, from `TODO.md:1335-1339`:

> Correct sequence: pilot -> users -> reliability -> partners ask -> API.
> OPA currently has no pilot, no revenue, no public API, no third-party auth
> model, no docs and no operational history.

**This materially qualifies `PARTNER_INTEGRATION_AND_DIFFERENTIATION.md`.** Its
integration surfaces are **a target architecture, not a build queue.**
`:1341-1345`: the first realistic integrators are **things that HAVE A TRIGGER
BUT NO BACKEND** - bluetooth panic buttons, smartwatches, elder-care pendants,
vehicle crash sensors. **Not competing safety apps.**

### 9b.7 THE DEVICE-DARK ANALYSIS - four states, one recoverable

If a phone has location revoked, is in airplane mode, is force-killed or powered
off, **no software safety app can transmit from it.** An OS and physics limit,
and it applies equally to every phone-based competitor.

| State | Capture | Transmit | Trail |
|---|---|---|---|
| Location revoked | no | yes | ends |
| **Airplane mode** | **yes - GNSS is receive-only** | no | **delayed, not lost** |
| Force-killed | no | no | ends |
| Powered off | no | no | ends |

**Airplane mode is the case 9c changes.** With a durable queue, every fix
captured during the dark period flushes on reconnect - *"here is where the phone
travelled during the two hours it appeared dark."* **Exactly what item 10's
airplane-mode test exercises, and exactly what ADR-014 must not throw away.**

**THE GAP: going dark is NOT an attested event.** `SILENT` is derived at read
time from fix age - **not persisted, not hash-chained.** **The chain is now ready
to carry such an event; nothing writes one.** That is a small, well-defined piece
of work and it is what completes the white paper's strongest claim.

**Being honest about all this is a commercial asset.** An institutional buyer
finds the limit anyway, and trusts whoever named it first.

**The one genuine software-only mitigation is SILENT ACTIVATION** - it reduces
how often the worst case is reached. **By the inclusion test it is CORE.**

### 9b.9 ADR-014 - THE ENDED-SESSION FIX CONTRACT. FULL CONTENT, DECIDED.

**Status when written: Accepted (design), Not Implemented.**

**THE PROBLEM.** `journey-ingestion.service.ts:107` throws
`ConflictException('Journey session has ended.')` for **any** fix addressed to an
`ENDED` session, before examining a single fix. So a batch buffered across a
supersession is rejected **entirely**, including fixes captured while the session
was still open. Item 10's airplane-mode test is exactly this scenario. **If this
is undecided when 9c is written, item 10 fails in a way that looks like a 9c bug
but is an undecided contract.**

It must also be reconciled with "never delete a queued fix until a 2xx" **in the
same code**: a permanent rejection means delete, a transient one means keep, and
the buffer cannot tell them apart unless the endpoint says so.

**THE DECIDED CONTRACT.**

A fix submitted against an `ENDED` session is:
- **Accepted** when `recordedAt < endedAt`
- **Permanently rejected against that session** when `recordedAt >= endedAt`
- **Retried** only for transient infrastructure failures

The endpoint must make those cases **machine-distinguishable**.

**Accepted** - `2xx`, including late-arriving fixes recorded before the session
ended.

**Permanently invalid for this session** - a specific client error with a stable
body:
```json
{
  "code": "FIX_RECORDED_AFTER_SESSION_ENDED",
  "retryable": false,
  "resubmit": "reacquire",
  "sessionId": "...",
  "endedAt": "...",
  "recordedAt": "..."
}
```

**Transient** - normal retryable semantics: `408`, `429`, `5xx`, timeout,
connection failure.

**THE QUEUE RULE:**
```
2xx                                  -> delete
retryable=false, resubmit=reacquire  -> RE-TAG and resend, do NOT delete
retryable=false, no resubmit path    -> delete and record permanent rejection
network / 408 / 429 / 5xx            -> keep
anything ambiguous                   -> keep
```

**The safety principle, restated:** *never delete until the server has either
accepted the fix or explicitly classified it as permanently unrecoverable.*

**BATCHES ARE PARTITIONED, NOT REJECTED.** For a batch spanning `endedAt`,
return per-item outcomes:
```json
{
  "accepted": ["idem-key-before-end"],
  "rejected": [
    { "idempotencyKey": "idem-key-after-end",
      "code": "FIX_RECORDED_AFTER_SESSION_ENDED",
      "retryable": false,
      "resubmit": "reacquire" }
  ]
}
```

---

**FOUR REFINEMENTS. Each was reached against a measured fact, and refinement 1
changes the contract materially.**

**REFINEMENT 1 - `retryable: false` MUST NOT MEAN "DELETE" HERE, BECAUSE ISSUE
17.13 WOULD TURN IT INTO SILENT PERMANENT LOCATION LOSS.**

The tracker never stops when the user leaves the SOS screen. `stopTracking()` is
called from exactly one place, and `if (running) return` means a second
activation no-ops **keeping the FIRST session's `sessionId`**. So after a
supersession the client keeps capturing fixes tagged with the **ended** session,
indefinitely, every one of them with `recordedAt >= endedAt`.

Under a naive "permanent -> delete" rule the server rejects each one and the
client dutifully deletes it. **The app looks like it is tracking. Nothing is
recorded. And this is precisely the emergency case, because supersession happens
when a NEW incident starts.**

**So `recordedAt >= endedAt` does not mean "this fix is invalid". It means "you
are addressing a session that is over."** Hence `resubmit: "reacquire"` - the
client calls `POST /journey/sessions` (idempotent by construction, safe on every
launch, one request), re-tags the queued fixes with the current session, and
resends. **The fixes survive.** Discard only if re-acquisition yields a session
the fix still cannot belong to, and log that as a real anomaly.

**REFINEMENT 2 - `endedAt` CAN BE NULL. SPECIFY IT.**
`SessionOverrides` types `endedAt` as optional, so `recordedAt < endedAt` is
undefined for an `ENDED` session with no `endedAt`. **A null `endedAt` on an
`ENDED` session means reject-and-reacquire, never accept.** Do not leave this to
a JS comparison against `null`, which coerces to 0 and would accept nothing while
appearing to have decided something.

**Also: `endedAt` is NOT currently selected.** `journey-ingestion.service.ts:97`
selects `{ id, userId, status, startedAt }`. The query changes too.

**REFINEMENT 3 - SEQUENCING. THE PER-ITEM BODY SILENTLY BREAKS THE CURRENT
CLIENT.**
Today the client deletes on 2xx. If the endpoint starts returning 2xx with
per-item outcomes, a half-rejected batch reads as full success and the rejected
fixes are deleted unexamined. **Server and client changes must land in the same
commit, or the server change must ship AFTER the client learns to parse the
body.** This is an ordering constraint, not a design detail, and belongs in the
ADR.

**REFINEMENT 4 - THE IN-ORDER FLUSH INVARIANT, WHICH 9c MUST PRESERVE.**
`893d65a` orders the newest fix by `receivedAt DESC, sequence DESC`. That is
correct **only because the tracker flushes in capture order, oldest first.** If
9c's persistence ever retries a failed old batch AFTER newer batches succeeded,
the newest `receivedAt` would carry the OLDEST `recordedAt`, and the tracking
page would show a stale position as current. **Either 9c preserves in-order
flushing as an explicit invariant, or the latest-fix query moves to `recordedAt`.
Write the invariant down now - cheap to preserve, expensive to discover.**

---

**AN OPEN SCOPE QUESTION FOR ADR-014, worth deciding deliberately rather than by
omission.**

`journey-ingestion.service.ts:114-127` runs the future-skew and
precedes-session checks **inside `dto.fixes.map()`, throwing
`BadRequestException`**. So **one fix with a bad `recordedAt` 400s the entire
batch of up to 200** - the identical whole-batch defect ADR-014 is fixing for
ENDED, and the same shape as 17.6's negative-speed gap where one stationary-phone
`speed: -1` kills 200 fixes.

**If ADR-014 gives ENDED per-item outcomes but leaves skew whole-batch, the
endpoint has two contradictory policies for "one bad fix in a batch" and the
client needs two code paths.** **Recommendation: one policy, applied to both.**

**WHAT ITEM 10 SHOULD THEN ASSERT:** buffered fixes recorded before supersession
drain successfully after reconnect; fixes recorded after the prior session ended
are re-tagged to the current session and drain too; nothing is silently lost; and
any genuinely discarded fix has an auditable reason.
