## 3. THE NOTIFICATION PROVIDERS - THE MOST SERIOUS FINDING
================================================================================

### 3.1 ADR-015 SECTION 6b, THE PRINCIPLE BEING VIOLATED [I]

"A provider that cannot deliver MUST return failure. A stub, an unimplemented
[channel]..." - and the architectural reason: the dispatch worker records
delivery outcome from the provider's own report.

### 3.2 MEASURED STATE OF ALL FIVE [M]

| Provider | Implementation        | 6b compliant | Notes                    |
|----------|-----------------------|--------------|--------------------------|
| SMS      | Real, africastalking  | YES          | false when unconfigured  |
| Email    | Real, Resend          | YES          | false when unconfigured  |
| WhatsApp | STUB - console.log    | NO           | returns success:true     |
| Push     | STUB - console.log    | NO           | returns success:true     |
| Voice    | STUB - console.log    | NO           | returns success:true     |

[M] whatsapp.provider.ts is 24 lines. It logs recipient and message to the
console, then returns success:true with a messageId of `wa-${Date.now()}` -
a fabricated identifier. push.provider.ts and voice.provider.ts are the same
shape.

[M] THE CONSEQUENCE, STATED PLAINLY: the dispatch worker marks a notification
SENT when a provider reports success. Three channels always report success.
THE PRODUCTION DATABASE THEREFORE CONTAINS RECORDS OF SUCCESSFUL WHATSAPP,
PUSH AND VOICE DELIVERIES THAT DID NOT OCCUR. The hash-chained timeline
faithfully preserves those false claims - the integrity machinery works
correctly on data that is not true.

[R] ANY PILOT REPORT SHOWING "NOTIFIED VIA FOUR CHANNELS" IS WRONG. This is
the kind of discovery that ends an institutional relationship permanently.

### 3.3 SMS - NOW CONFIGURED AND DELIVERING [M]

sms.provider.ts reads three variables through BARE process.env:
  AFRICASTALKING_API_KEY
  AFRICASTALKING_USERNAME
  AFRICASTALKING_SENDER_ID

NONE of the three exist in App Service settings. The full alphabetical list
was read in the portal; AFRICASTALKING_* would sort before ALLOWED_ORIGINS and
is absent.

[M] The provider handles this CORRECTLY - it warns and returns success:false
with 'SMS provider not configured'. It does not lie. But no SMS has ever been
sent from production.

[M] ADR-015 criterion 3 predicted exactly this: "Variables read through bare
process.env are the ones most likely to be missed, because they bypass
whatever configuration surface was used to set up the environment."

[M] normalizePhone hardcodes +234. The provider is Nigeria-only by
construction. Fine today; relevant to any multi-country conversation.

[M] RESOLVED THIS SESSION. Three App Service settings were added:
  AFRICASTALKING_USERNAME   = OPASafety
  AFRICASTALKING_API_KEY    = the OPA Safety app's PRODUCTION key

### 3.5 AN UPDATED EMERGENCY CONTACT DID NOT RECEIVE THE ALERT [M]

[M] OBSERVED: the emergency contact phone number was changed in the app, and a
subsequent alert still went to the OLD number.

[R] HYPOTHESIS, NOT YET MEASURED - do not act on this without checking:
dispatch Phase 2c-1 stores a DURABLE JSON PAYLOAD on the outbox row, built by
buildNotificationPayload() at INCIDENT-CREATION time. Throughout this session
the app reported "existing emergency alert remains active" and REUSED the
session rather than creating a fresh incident. A payload written when the
original incident was created would carry the contact as it stood THEN.

[R] IF THAT IS THE MECHANISM, IT IS CORRECT BEHAVIOUR BADLY SURFACED. The
payload is deliberately immutable so a crash cannot lose it - that is the whole
point of the outbox. But a user who updates their emergency contact and still
sees alerts go to the old number will call it a defect, and in a safety product
they would be right to.

[R] MEASURE FIRST: confirm whether the alert came from a REUSED incident or a
NEW one. If new, the hypothesis is wrong and the cause is elsewhere - contact
resolution, caching, or a stale token. If reused, the design question is
whether a contact change should invalidate pending payloads, and that is an
ADR-shaped decision rather than a bug fix.

### 3.4 THE FIX FOR THE STUBS [R]

Three files, a few lines each. Return success:false with an error naming the
channel unimplemented, matching the SMS pattern. Add a test per provider
asserting the false. No credentials, no procurement, no external dependency.

[R] DO THIS BEFORE ANY PILOT DEMO. It converts a false claim into an honest
"not yet available", which is what the honesty guardrail requires and what a
hospital would expect.

[I] Ultra 25 section 7.4, carried through Ultra 26 and 27: ADR-013 and ADR-015

[M] ADR-015 - "OPA as a hardware and telemetry event middleware, with the
mobile application as a first-class client". 493 lines. Drafted 31 July from a
founder draft with SIX factual corrections applied and recorded, plus two more
in later passes. It is the best-reasoned document in the project.

[D] THE FOUNDER CONFIRMS THE PIVOT IS DECIDED and that ADR-015 was crafted for
it. THE ADR HAS BEEN SITTING UNINSTALLED SINCE 31 JULY. This is the Ultra 26
section 8.1 failure mode - generated, never committed, unnoticed - with the
longest run of any instance, and it applies to the decision everything else
now depends on.

[M] WHAT ADR-015 DECIDES, in brief:
  - OPA is a multi-entry incident platform; mobile is one client among
    hardware, partner systems and future channels.
  - Entry points are PARALLEL, not sequential.
  - Ingestion route flat and unprefixed - main.ts sets no global prefix and
    redactSensitivePath depends on that shape (trap #53). Proposed
    /integrations/device-events; the path is not frozen, the convention is.
  - Fixed devices carry an INSTALL-TIME location. This sidesteps indoor
    positioning rather than solving it.
  - The Command Centre becomes REQUIRED rather than optional, at ADR-013's
    VIEWER-NEVER-CONSOLE scope.
  - 9c stays Tier-1 and was explicitly NOT downgraded.
  - THE HARDWARE OWNERSHIP MODEL IS DEFERRED, and this is the single schema
    question everything depends on. Incident.userId is required with
    onDelete: Restrict, and both the advisory lock and the one-active-session
    partial index key on it. A wall panel has no human principal.
  - A "virtual system user" shadow row is REJECTED as the committed model.
    Preferred direction: an explicit IntegrationPrincipal / DevicePrincipal
    associated with a Facility, with nullable initiatedByUserId /
    initiatedByPrincipalId and a constraint ensuring exactly one initiator.
  - PREREQUISITE: measure every schema and orchestrator dependency on
    Incident.userId BEFORE choosing.
  - Roadmap delta: Sprint 11.5 device model, device auth, ingestion endpoint,
    trigger enum values -> Sprint 12 repurposed to device and event logging
    -> Sprint 13 Command Centre at viewer scope.
  - STAFF vs CLIENTS is answered as NEITHER: the partner's DEVICES are
    enrolled, not people. Simpler, and a materially easier NDPA position.
    To be confirmed rather than assumed.

[M] ADR-013 holds the VIEWER, NEVER CONSOLE boundary. [R] INSTALL IT BEFORE
COMMAND CENTER CODE. A hospital asking for "assign this nurse" or "mark
ambulance en route" is asking for console. ADR-015 item 5 anticipates this:
"A partner asking for dispatch is the pressure ADR-013 anticipated; it does
not by itself reverse that decision." A written boundary is what lets you say
no without re-litigating it under customer pressure.

[R] WHILE THE INSTALLER IS OPEN, fix ADR-014 section 11's structural
asymmetry - four unheaded prose decisions above eight `####` subsections.
Flagged in Ultra 26 section 7.4, carried in Ultra 27, two minutes to fix.
