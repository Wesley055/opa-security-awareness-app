### 9b.1 ADR-016 SHIPPED - THE FULL EVIDENCE CHAIN

**Every link measured. This is the section to quote about the readiness fix.**

**1. The design decision (blocker A / q51), settled by argument then built.**
The required-dependency set had to be **reviewable** (a reader sees at a glance
that Redis is not required) AND **testable** (D5's graduation case must be
writable without inventing a test-only hook, since D4 forbids an env toggle).

Three shapes were considered. **A pure policy module won.** A third constructor
parameter was rejected because Nest resolves by `design:paramtypes` and would
try to inject a `Set` provider - a default value does not prevent that.

**2. The mutability defect, caught in review before it shipped.** The first
draft exported `REQUIRED_DEPENDENCIES: ReadonlySet<ReadinessDependency>`.
**`ReadonlySet` is a compile-time view only; the underlying `Set` stays mutable
at runtime**, so an importer could cast it and `.add('redis')` - making policy
drift dynamically, exactly what D4 forbids. **Replaced with a frozen tuple as
the exported policy and a private Set for lookups.** Verified at runtime:
`REQUIRED_DEPENDENCIES.push('redis')` **throws**, length stays 1.
**`readiness-policy.spec.ts` asserts `Object.isFrozen(...)` precisely because
`readonly` and `ReadonlySet` vanish at compile time.**

### 9b.3 THE INSTALLER DISCIPLINE - 44 FOR 44, WITH THREE NEW RULES EARNED

Six installers, 7/11/11/12/12/11 replica cases, **every case re-run in full
after every revision.**

**1. PIN THE WHOLE-FILE RESULT SHA, NOT JUST THE FRAGMENTS.** Trap #108, and the
most valuable thing learned this session. **Three independent replica cases** -
step 3 C8, step 5 C7, CI C8 - inserted an unrelated line elsewhere in the source.
**Every fragment check passed: anchors found exactly once, `anchorAfter`
correct.** Only the result SHA caught it. Compute it over the EOL-normalised
planned OUTPUT so it is independent of EOL/BOM/trailing-newline, which are
preserved separately.

**2. BEHAVIOURAL INVARIANTS BELONG IN PHASE 1 AS WELL AS PHASE 2.** Step 3's
first version checked invariants only after writing, so a tampered installer
modified a TRACKED file and needed `git checkout` to recover. Moved to run on
the planned array too. **Rebuilt, the same case aborts with the file untouched
at 53 lines.**

**3. SEMANTIC CHECKS SURVIVE A REGENERATED SHA; A SHA DOES NOT.** Every
installer was tested against a tampered CONTENT array with `EXPECT_SHA`
regenerated. **The SHA gate printed "matches the reviewed draft" every time.**
What caught the tamper:
- step 1: required-set members parsed from the whole declaration block -> `[database, redis]`, 2 members
- step 2: `it()=6 it.todo()=1` instead of 7/0
- step 3: `allUp=1`
- step 4: `skip/only=1`
- step 5: `new_description=0`
- CI: `guard=0 any_if=0`

**4. A DEPENDENCY GUARD MUST CHECK EXPORTED DECLARATION FORMS.** The first
version was `depText.indexOf(sym) !== -1 && depText.indexOf('export ') !== -1`,
which **degenerates into a substring search** - one `export` anywhere satisfies
the clause for every symbol. **A decoy file with the four names in a COMMENT, a
non-exported `const dependencyState`, and one unrelated export PASSED it.**
Fixed to `^export\s+function\s+NAME\s*\(` style, anchored, asserted by count.

**5. AN IDEMPOTENCY OR ABSENCE CHECK MUST BE ANCHORED, NOT A SUBSTRING.**
Measured: `readiness-policy.spec.ts` contains the string `it.todo` **in a
comment** referring to the todo it replaces. A substring gate would have failed
on its own correct content. Anchored to `^\s*it\.todo\s*\(`.

**6. VERIFY THE PUBLISHED ARTIFACT'S GUARDS AGAINST ITSELF.** Extract the
CONTENT array from the `.txt` about to be downloaded, hash it, compare with the
embedded `EXPECT_SHA`. Done for every installer.

**7. TRAP #104 FIRED AGAIN.** Step 5's case 11 harness silently failed to apply
its tamper (`BLOCK_NEW` still 5 lines), so the installer ran normally and
succeeded - **which could have been read as "the tamper was accepted".**
**Rebuilt with `if(before===after){console.log('HARNESS FAILED');process.exit(2)}`.**

**8. A CORRECT REFUSAL IS NOT A FAILURE.** Step 5 refused on first run:
`FAIL target has no trailing newline; refusing to guess`. Every content check
had passed; only the file-ending assumption was wrong. **Nothing was written.**
The fix was to treat trailing newline as a preserved property like BOM, not to
force it. **The SHA did not change**, because it pins content lines in canonical
form.

4. **Duress cancel.** `handleCancel` never calls the API.
5. **Hardware trigger** (triple power press / held volume-down) - **80% of
   wake-word for 10% of the cost, no mic, no App Store risk, no NDPA audio
   question. BEFORE voice. This is the actual silent-activation mechanism.**
6. **Automated incident report on resolution.** The OUTPUT of everything 10B
   built, and **the sellable artifact in the partnership model.**

### Silent activation - the unasked design question

**Backend ready. App NOT silent** - five-second visible countdown, full-screen
state changes, large button. **THE DESIGN QUESTION NOBODY HAS ASKED: if
activation is silent, how does the user know it worked?** Screen confirmation
defeats the purpose. **A single discreet haptic is the likely answer. Decide
before building.** It interacts with the `contactsNotified` defect: a user who
cannot look at the screen has no confirmation channel at all.

### Positioning - "live" is EARNED, "background" is NOT

**Rejected: "emergency coordination platform."** **Adopted:** *emergency
alerting with a verifiable location record* / *live incident awareness*.
**"Live" is earned as of `d5aca8b`** - 50 fixes, 10s cadence, verified chain.
**Caveat: live WHILE THE APP IS IN THE FOREGROUND.** `source: 'background'` is
unreachable. **Do not let "live" grow into "always".**

**HONEST CAPABILITY STATEMENT:** *records continuously while the app is open, at
a verified 10-second cadence, on a tamper-evident chain.*

**Two words to avoid** (ADR-015): **"immutable"** - the chains are
**tamper-evident**; and **on-device Picovoice processing is NOT an existing
asset**.
